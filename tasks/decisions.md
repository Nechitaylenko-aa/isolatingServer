# Журнал архитектурных решений (fcpp-agent ADR)

**Незыблемые принципы:**

1. **Unix:** делать одно, но делать хорошо. Только C++/CMake/Ninja. Никакого функционала сверх ТЗ.
2. **Закрытая безопасность:** всё, что явно не разрешено, — запрещено.
3. **Zero-Search:** агент ничего не ищет и не угадывает. У каждой сущности строгое место (флаг / конфиг / стандарт). Нет в указанном месте — нет в природе → генерация нового или FAIL.

## Блок 1: Инфраструктура, CLI и Хранение данных

### ADR-01: Точный набор CLI-команд (Пункт 1)
* **Контекст:** Минимальный расширяемый набор команд. CLI — тонкий клиент к deterministic API (не ядро).
* **Предложенное решение:**
  - **MVP (жёстко):** `init`, `open <path>`, `close`, `projects`, `ask "<text>" [--json]`, `build [target]`, `test`, `tidy`, `status`, `index <status|refresh|rebuild>`.
  - **Флаги:** `--config PATH`, `--project PATH`, `--compile-commands PATH`, `--yes`, `--json`, `--verbose`.
  - **Exit codes:** `0` success; `1` typed error (§59); `2` usage error.
  - **Вывод:** human-readable по умолчанию; `--json` — machine-readable. Стриминг активен всегда.
  - **REPL:** только если stdin — TTY. Голый текст = `ask`. Без меню и подсказок-эвристик.
  - **Запрещено в MVP:** `serve`, `use`, `config`, GUI-подобные интерактивные сценарии, авто-роутинг admin-команд через LLM.
  - Все команды = 1:1 методы Agent API.

* **Статус:** ✅ Утверждено

### ADR-02: Точная SQLite schema и механизм миграций (Пункты 2, 19)
* **Контекст:** Персистентный индекс. Версионируемая схема, независимая от версии агента/API.
* **Предложенное решение:**
  - Одна БД на проект, вне исходников: `~/.fcpp-agent/db/<hash>/index.db`. `PRAGMA journal_mode=WAL; foreign_keys=ON; busy_timeout`.
  - **Таблицы (суть):** `schema_meta(key,value)`; `project(canonical_path,build_dir,last_indexed_at,generation)`; `index_generation(generation,state)`; `file(path,generation,mtime,size,hash)`; `symbol(id,generation,usr,kind,qualified_name,file_id,parent_id,flags)`; `symbol_location(symbol_id,file_id,line,col,end)`; `include(from_file,to_path,resolved_file)`; `inheritance(derived,base,access)`; `override(method,base_method)`; `reference(symbol_id,file_id,line,col)`; `call(caller,callee)`; `compile_command(file_id,directory,arguments)`.
  - **Миграции:** нумерованные чистые SQL-файлы `migrations/NNNN_*.sql`; runner читает `schema_meta.schema_version`, применяет по возрастанию, каждая в `BEGIN IMMEDIATE`; ошибка → `ROLLBACK`, стоп. Введение `min/max_compatible_schema`. Downgrade не поддерживается (→ `index rebuild`).
  - Смена семантики индекса → новая generation + reindex, не конвертация на месте.
  - До миграции — бэкап `index.db.bak`.
  - Никаких prompt/LLM-текстов в БД.

* **Статус:** ✅ Утверждено

### ADR-03: Формат project mapping и параллельные сессии (Пункты 3, 20)
* **Контекст:** Сопоставление проекта и его БД; поведение при параллельных CLI.
* **Предложенное решение:**
  - **Zero-Search:** проект определяется строго по каноническому пути CMake-корня — из `--project` или из конфига. Никаких эвристик поиска/подбора.
  - **Единая БД агента:** реестр и индекс хранятся в одной SQLite-БД агента (`~/.fcpp-agent/projects/registry.db`); полный набор миграций применяется к ней целиком.
  - Таблица реестра — `registry_project(project_id PK, canonical_path UNIQUE, db_path, last_opened_at, created_at)` (имя `registry_project`, а не `project`, чтобы не конфликтовать с per-project таблицей индекса `project`). `project_id` — непрозрачный (`project-<hash>`), **не равен пути** (§89.3.1). `db_path` детерминированно из `sha256(canonical_path)[:16]`.
  - Нет пути в реестре и нет `CMakeLists.txt` в нём → FAIL с диагностикой.
  - **Блокировки:** WAL + `busy_timeout` → параллельное чтение, один писатель. Межпроцессно — `flock` на `index.lock`: `SHARED` для readers/refresh, `EXCLUSIVE` для rebuild. Конфликт → `INDEX_BUSY`/`PROJECT_BUSY` (`retryable=true`).
  - `index.rebuild` — атомарно: `BUILDING` → `ACTIVE`; ошибка не уничтожает валидную generation.
  - Пишущие транзакции — `BEGIN IMMEDIATE` + батчевые фиксации.

* **Статус:** ✅ Утверждено

## Блок 2: Индексация, Парсинг C++ и CMake

### ADR-04: compile_commands.json и работа с CMake (Пункты 6, 16)
* **Контекст:** Источник флагов компиляции для libclang; политика post-patch сборки.
* **Предложенное решение:**
  - **Zero-Search. Только три источника, по приоритету:**
    1. `--compile-commands <path>`;
    2. конфиг проекта (`compile_commands=<path>`);
    3. `<root>/build/compile_commands.json`.
  - Рекурсивный поиск по дереву — **запрещён**. Не найден — **немедленный FAIL** (`COMPILE_COMMANDS_MISSING`). Автогенерация cmake «на угад» — **запрещена**.
  - Без `compile_commands.json` индексация C++ не выполняется (ADR-06).
  - **Post-patch сборка:** строго `cmake --build <build_dir> --target <target>` — инкрементально, конкретный таргет. Без debounce, без clean, без reconfigure в авто-режиме. Изменены CMake-файлы / нет build-dir / `allow_exec=NO` → STOP, сборка не запускается.
  - Результат сборки кэшируется по (generation, target, mtime-набор).

* **Статус:** ✅ Утверждено

### ADR-05: Сущности индекса, stale index и перформанс (Пункты 4, 5, 17, 18)
* **Контекст:** Что извлекать, как определять устаревание и точку обновления, лимиты MVP.
* **Предложенное решение:**
  - **MVP-сущности (libclang):** translation unit/file, namespace, class, struct, union, enum(+constants), typedef/using/alias, function, method, constructor, destructor, variable, field, parameter, inclusion, base specifier, reference, call expression. Хранение: `kind`, `qualified_name`, **USR**, позиция, access, flags. Шаблоны/лямбды/макросы — пост-MVP.
  - **Stale index (по уровню стоимости):**
    1. инвалидация окружения: изменился `compile_commands.json` / `CMakeLists.txt` / версия backend / `schema_version`;
    2. быстрый проход `stat`: `mtime`+`size`;
    3. подтверждение по content hash — только для кандидатов из (2); hash совпал → актуален, только `mtime`;
    4. новые/удалённые файлы → add/drop (CASCADE);
    5. транзитивные зависимости по графу `include` → переиндексируются только затронутые TU (правка `.h` не пересобирает весь индекс);
    6. неразрешимые include/макросные зависимости → `dirty`, консервативный reparse.
  - **`index.refresh`:** для каждого `dirty_tu` (лексикографический порядок) — delete строк TU → parse → batch insert, в рамках активной generation. Пусто `dirty_tu` → no-op.
  - **Контекст в LLM = минимум (Zero-Window):** файлы `.cpp/.hpp` **никогда не отправляются целиком**. Из SQLite/libclang вырезаются строго: тело запрошенного метода (по SourceRange) или сигнатура класса/enum. Зависимости — только «скелет»: forward declarations + public-интерфейс из БД. Приватное и тела inline не передаются.
  - **Лимиты MVP (soft):** ≤5 000 TU, ≤1 млн строк, per-TU timeout, `build_timeout`. Сверх лимита — предупреждение, обработка порциями.
  - **libclang-память:** RAII-обёртки (`CXTranslationUnit/CXIndex/CXString/tokens`), обязательный dispose, `SkipFunctionBodies` где тела не нужны, ограничение числа одновременных TU, опциональный изолированный `IndexWorker`-процесс.

* **Статус:** ✅ Утверждено

### ADR-06: Отсутствие libclang / cmake / clang-tidy (Пункт 12)
* **Контекст:** Поведение при отсутствии инструментов.
* **Предложенное решение:**
  - **Single-user, фиксированная среда (зафиксировано):** агент персональный. Поддерживается ровно один стек — **C++20, clang/libclang 22, CMake + Ninja** (FreeBSD). Любое отклонение — **жёсткая ошибка с описанием и остановкой** без деградации и продолжения. Никаких «вежливых» fallback под чужую среду.
  - **Critical:** `cmake`, `compile_commands.json`, libclang. Нет любого → **жёсткая ошибка конфигурации** (`COMPILER`/`BUILD_NOT_CONFIGURED`), работа прекращается.
  - **Версия libclang/clang (зафиксировано):** целевая — **clang/libclang 22**; она назначается **по умолчанию** в конфиге (`tool_clang_path`) сознательно, чтобы как можно дольше не менять компиляторный фреймворк. Бэкенд абстрагирован (§2.2), версия — деталь реализации. Наличие других версий (14/19/20) не меняет дефолт.
  - **Сборка/инструменты:** **Ninja используется везде, где это даёт выигрыш** (сборка агента, сборка/тесты проектов под управлением агента). При отсутствии Ninja — допустим fallback на генератор по умолчанию (см. ADR-04).
  - **Запрещено:** Tree-sitter, регулярные выражения, «нативные лексеры» как замена компилятора. Любой fallback-парсер даёт ложные доказательства и нарушает §57/§87.
  - **Important:** `clang-tidy`, `ninja`, `ctest` — деградация только этих: `tidy`/`tests` возвращают типизированную ошибку, index/ask/build работают.
  - **`fcpp doctor`:** preflight-таблица инструментов (найден/версия/путь/класс) + команды установки (FreeBSD pkg / Linux). Выполняется на `open`/`init`.
  - Конфиг: `tool_*_path` override (дефолт clang → llvm22); `enable_tidy=YES|NO`. Агент не устанавливает пакеты.

* **Статус:** ✅ Утверждено

## Блок 3: LLM, Безопасность и Бюджет контекста

### ADR-07: Интеграция с LLM (Пункты 7, 8, 9)
* **Контекст:** Формат обмена, настройки llama-cpp, стриминг.
* **Предложенное решение:**
  - **Формат:** лаконичный XML в стиле Aider (`<intent>`, `<answer>`, `<patch>`), не Tool Calling. Причина: LLM не оркестратор (§5/§83); XML стримится и парсится одинаково на всех backend. Парсер — тег-парсер (не regex), валидация по enum, 1 retry-repair → `LLM_INVALID_RESPONSE`.
  - **llama-cpp `prompt_cache` обязателен:** неизменяемый префикс (system prompt + схема БД + few-shot) на роль, детерминированный порядок контекста → считается только суффикс. `temperature` низкая для lite; фиксированный `seed`; keep-alive весов.
  - `same_as_main` резолвится router; роли не привязаны к моделям.
  - **CLI-стриминг обязателен:** стримится `<answer>`; `<intent>`/`<patch>` аккумулируются и валидируются целиком.
  - Отмена — cooperative; частичный XML не применяется.

* **Статус:** ✅ Утверждено

### ADR-08: Безопасность: whitelist и подтверждения (Пункты 10, 11)
* **Контекст:** Что выполняется без вопроса, что требует Y/N.
* **Предложенное решение:**
  - **Закрытая модель:** Effect вычисляет deterministic core (`READ_ONLY < WRITE_SOURCE < EXECUTE < WRITE_BUILD`), не LLM.
  - **Whitelist (без подтверждения, при `allow_*`):** read = index/outline/callers/callees/refs/includes/status; exec = `cmake --build`, `cmake -S -B`, `ctest`, `ninja`, `tidy`. Проверка по `argv`: basename ∈ whitelist + допустимые флаг-шаблоны.
  - **Инъекции:** запрещены shell-метасимволы (`;|&&$(...)`), redirection, выход за build-dir. Вызовы — только через `execv(argv)`, не через shell.
  - **Обязательный Y/N:**
    - `WRITE_SOURCE` (`apply_patch`): показ diff, применение только после `Y`; non-interactive — FAIL без `--yes`.
    - Любой `EXECUTE` вне whitelist / любой shell → Y/N; non-interactive → FAIL.
  - **Запрещено:** `rm`, `curl`, `wget`, `sh -c`, `perl -e`, `sed -i`, `awk` для правки исходников (§45).
  - Клиент не повышает permission через API (§89.40). Секреты не попадают в diff/log/prompt (§61).

* **Статус:** ✅ Утверждено

### ADR-09: Context Budgeting, Subtasks, Remote (Пункты 13, 14, 15)
* **Контекст:** Упаковка контекста, подзадачи, изоляция выполнения.
* **Предложенное решение:**
  - **Zero-Window:** в LLM уходит технический минимум из Evidence. Никаких файлов целиком. Строго: сигнатуры / тела затребованных методов / relationships. Зависимости — только скелет (forward decls + public API из БД). Раскрытие глубже — ленивое, по запросу planner'а.
  - **Лимиты на секцию:** `max_source_lines`, `max_symbols`, `max_callers`, `max_callees`, `max_refs`. Превышение → детерминированный top-N + summary. Дедупликация общих заголовков. Стабильный порядок секций (под prompt_cache).
  - **Subtasks:** `allow_subtasks=NO` → дочерних задач нет. При `YES` — отдельный subsystem; child наследует snapshot (project/session/editor/generation), возвращает только Evidence родителю. В v2.0 не обязателен.
  - **Изоляция:** `exec_target = local | docker | ssh`; единый `BuildSystem`-интерфейс, разные backend выполнения. Index/файлы локальны; на удалённую сторону — только команда. Подчиняется ADR-08; секреты не покидают хост.

* **Статус:** ✅ Утверждено


### ADR-10: Детерминированная обработка галлюцинаций и каскад моделей (Пункт 7.1)

* **Контекст:** Обнаружение ошибок локальных/слабых моделей и автоматическое делегирование (Lite → Main → Cloud).
* **Предложенное решение:** Триггеры детерминированного обнаружения глюков (Glitches/Hallucinations):
1. Агент считает ответ модели ошибочным, если срабатывает хотя бы один объективный критерий:
  - Syntax Fail (Нарушение формата): Модель выдала невалидный XML/JSON, не закрыла тег <patch> или выдала пустой ответ.
  - Reference Fail (Вымышленные сущности): Модель предлагает изменить метод или файл, которого нет в индексе SQLite (галлюцинация путей или имён).
  - Compilation Fail (Сломанный код): Код после применения <patch> не проходит синтаксический чек через libclang (ошибки компиляции, которых не было до патча).
  - Loop Fail (Зацикливание): Модель генерирует повторяющиеся токены или бесконечно вызывает одну и ту же подзадачу (превышен таймаут или лимит итераций).
2. Путь решения: Каскад моделей (Model Fallback Cascade):
Уровни моделей жестко прописываются в agent.conf (например: lite = Qwen-2.5-7B-Local, main = DeepSeek-R1-Local/32B, cloud = Claude-3.5-Sonnet-API).При обнаружении глюка запускается автоматическая цепочка:
	1. Шаг 1 (Самоисправление): На уровне lite делается ровно один (1) автоматический ретрай с добавлением ошибки в контекст («Ты нарушил XML-формат/сломал компиляцию, исправься»).
	2. Шаг 2 (Эскалация на Main): Если ретрай на уровне lite снова выдал ошибку — сессия замораживается, контекст передается на уровень main (более тяжелая локальная модель).
	3. Шаг 3 (Эскалация на Cloud): Если main выдает синтаксический брак или ломает код — запрос уходит на самый верхний уровень cloud (при условии, что в конфиге прописан API-ключ облачной модели).
3. Жесткий FAIL-safe стопор:
Если самый высокий доступный уровень модели (например, cloud или main, если облако отключено) не смог решить задачу за 1 ретрай, агент полностью останавливает выполнение:
	• Состояние файлов проекта автоматически откатывается до исходного (/revert / git checkout).
	• Выводится строгое сообщение:fcpp-agent: Ошибка обработки запроса. Цепочка моделей [Lite -> Main -> Cloud] исчерпана.
Причина: [Конкретный триггер, например: Патч нарушает компиляцию в src/main.cpp:42]
Действие: Измените ваш запрос или переключите конфигурацию моделей.
4. Запрещено: Бесконечные циклы ретраев, молчаливое игнорирование ошибок компиляции, применение «битых» патчей в надежде, что пользователь исправит руками.
5. **Уточнение (принято): детерминированная эскалация над ядром.**
   - **Решение об эскалации принимает детерминированный детектор, а не другая LLM.** Субъективное «модель глючит» — не триггер.
   - **Триггеры — только объективные:** Syntax Fail (невалидный/пустой XML/JSON), Reference Fail (сущность/путь/метод отсутствуют в индексе SQLite), Compilation Fail (libclang syntax-check до/после патча), Loop Fail (повторы токенов/подзадач, превышение итераций/таймаута), Schema Fail (ответ не соответствует структуре).
   - **Каскад по стоимости: lite → main → remote.** Платный/верхний уровень — только если нижестоящий реально не справился.
   - **Жёсткий бюджет:** ровно **1 авто-ретрай на уровень**, без циклов; суммарный лимит (например ≤3 попытки, ≤N токенов, ≤T секунд).
   - **Передача ошибки наверх:** при эскалации в промт добавляется конкретная причина («нарушен XML», «патч не компилируется в src/x.cpp:42»), иначе верхний уровень повторит ошибку.
   - **Монотонность риска:** эскалация **никогда** не разрешает операцию, запрещённую policy; сомнение только понижает Effect (§27).
   - **Стадии эскалируются независимо:** классификация Intent (lite→main) и генерация патча (main→remote) — раздельные цепочки.
   - **Каскад живёт НАД ядром** (`CRequestPipeline`/`CAskService`), а не внутри — детерминизм ядра не затрагивается.
   - **Hard-stop на вершине:** если верхний доступный уровень не справился за 1 ретрай — **стоп**, источник не изменяется (патч не применяется), выводится типизированное сообщение с причиной. Никакого «оставим как есть».
   - **Принцип первопричины:** сначала исправляется evidence/plan/prompt, и только затем повышается модель. Эскалация — для редких сложных случаев, а не для компенсации систематических ошибок классификации.
   - **Реализация:** Этап 6c; переиспользует уже имеющиеся детекторы (`CIntentAnalyzer` XML-валидация, `CRequestPipeline::resolve_subject` Reference Fail, patch validate, будущий libclang syntax-check).
* **Статус:** ⏳ На рассмотрении

### ADR-12: Политика версионирования схемы и порядок этапов (LLM last)

* **Контекст:** До первого рабочего релиза схема активно меняется; при этом архитектура требует детерминированного ядра и запрещает LLM быть оркестратором (§5/§83/§92).
* **Предложенное решение:**

  **1. Версионирование/миграции — только с v1 (✅ принято).**
  - До первого работающего релиза — **никаких нумерованных миграций и версий схемы**. Схема задаётся **единым baseline-файлом** (`CREATE IF NOT EXISTS`), свободно правится при разработке.
  - Строгое версионирование включается ровно в момент «v1 заработал», когда появляется персистентность, которую нельзя терять.
  - **`index.db` — кэш, восстановимый из исходников** → при несовместимости: не конвертировать, а **пересоздать generation**. Миграции для кэша не обязательны.
  - **`registry.db` — единственное пользовательское состояние** (список проектов), но восстановимо повторным `open` при single-user.
  - Тесты не привязываются к точной версии схемы.

  **2. Порядок этапов: детерминизм вперёд, LLM — в последнюю очередь (✅ принято).**
  - **LLM last** — модель только интерпретирует запрос и формирует ответ/патч.
  - **`Intent` IR и Evidence Planner — детерминированный код**, не LLM: `Intent`-структуры, table-driven `Intent → [tools]`, Context Budget, patch validate/policy — всё делается **до** подключения модели.
  - «Intent last» **неверно**; «LLM last» — верно.

  **3. Точный порядок реализации.**
  1. **8a — инфраструктурный минимум:** `allow_read/write/exec` (§47), `fcpp doctor` (ADR-06), structured logging (§60), персистентная сессия («текущий проект»).
  2. **6a — детерминированное ядро запроса:** `Intent` IR, Subject Resolver (надстройка над `cursor_at`), Evidence Planner (table-driven). Проверяется ручным `Intent` в CLI без LLM.
  3. **7a — patch-pipeline без LLM:** parse → validate → policy → apply → post-patch `cmake --build --target`; вход — патч из файла/stdin. Требует §47 (`allow_write`) и интеграции `CExecutor`.
  4. **8b — Agent API:** CLI становится тонким клиентом (§93); API **не** экспонирует `Intent/Area/Relation` (§89.39).
  5. **6b — LLM-биндинг:** `lite` заполняет `Intent`; `main` формирует ответ/патч (llama.cpp, `prompt_cache`, стриминг, XML Aider-style).
  6. **7b — полный цикл изменения:** LLM генерирует патч → конвейер 7a.
  7. **Каскад моделей (ADR-10) + benchmark классификации (§71–72).**

  **Ограничения порядка:** patch-apply не делать раньше §47; API не связывать с `Intent`; `CExecutor` подключать до patch-apply.

* **Статус:** ✅ Принято

### ADR-11: API-поверхность слоя libclang (что берём от clang заранее)

* **Контекст:** Детерминированный core должен получать от libclang заранее известный, стабильный набор запросов. Состав API фиксируем до реализации, чтобы не менять его при добавлении инструментов.
* **Предложенное решение:**

  **Принципы слоя.**
  - Слой **не строит графы/резолвинг сам** — максимально делегирует libclang (детерминизм, меньше собственного кода).
  - Все запросы — по стабильным идентификаторам (`USR`), не по именам/путям.
  - Каждый запрос — типизированный результат + типизированная ошибка (Секция 3).
  - libclang — только read-only анализ. Изменение кода — через patch (ADR-04/§45).

  **A. Локация курсора → сущность (§21, §51).**
  - `cursor_at(file, line, col)` → `USR` (ближайшая семантическая сущность; предок при попадании в тело).
  - Семантика «этот класс/эту функцию» через ближайший охватывающий `USR`.

  **B. Описание сущности (§34, §35).**
  - `outline(USR)` — дети (методы/поля/вложенные типы) с сигнатурами, access, флагами.
  - `signature(USR)`, `source_range(USR)` (для Zero-Window-среза §34/ADR-05).
  - `get_canonical(USR)` — каноническая декларация (для дубликатов объявление/определение).

  **C. Типы (§15).**
  - `type_of(USR)` — тип сущности/поля/параметра; `resolve_type` до named-типа.
  - `result_type(USR)`/`param_types(USR)`.
  - `points_to(USR)` / `pointee(USR)` / `referenced(USR)` (последнее — встроенный `clang_getCursorReferenced`, важно для callers).

  **D. Иерархия (ключевой сценарий заказчика).**
  - `base_types(USR)` — прямые базовые типы.
  - `ancestors(USR)` — подъём по цепочке до корня (protected/private/virtual).
  - `derived_types(USR)` — прямые наследники (из БД, т.к. libclang не имеет глобального reverse-поиска).
  - `overrides(USR)` — методы, переопределяющие данный (в наследниках).
  - **`dispatch_targets(USR)` — сквозной резолв виртуального/чисто-виртуального метода до всех реализаций в наследниках:**
    1. `base = get_canonical(USR)`; 2. `derived = derived_types(base)`; 3. `overrides = overrides(base)`; 4. объединить с базовым `USR`.
  - **`base_of_override(USR)` — обратный подъём от реализации к объявляющему базовому методу.** Это два зеркальных запроса (§38).

  **E. Вызовы и ссылки (§36, §37, §39).**
  - `callers(USR)` — места вызовов; через `clang_getCursorReferenced` на `CallExpr`/`DeclRefExpr` (не по имени).
  - `callees(USR)` — что вызывает функция.
  - `references(USR)` — все использования (тип/значение/вызов), позиции.

  **F. Специальные члены (§15).**
  - `specializations(USR)` — ctor/copy/move ctor и dtor, виртуальный dtor.

  **G. Include-граф (§40).**
  - `file_includes(file)` — прямые включения; `included_by(file)` — обратные (из БД).
  - `resolve_include` — резолв `InclusionDirective` в `file` (Zero-Search в пределах известных TU).

  **H. Макросы (пост-MVP, задел).**
  - `macro_definition_at`, `macro_expansions(USR)`, `macro_for_usr`. Заложить в интерфейсе, реализовать позже.

  **I. Диагностики (задел для verify — §42/§43).**
  - `diagnostics(tu)` — ошибки/предупреждения компиляции (используется валидатором патчей, ADR-10 Cascade).
  - `syntax_only_compile(tu)` — проверка «патч сломал/не сломал компиляцию».
  - Точные/системные диагностики при необходимости.

  **J. Обход TU (§15).**
  - `visit_tu(file, visitor)` — детерминированный обход верхнего уровня (без обхода тел, если не нужны).

  **Организация кода (по `rules.md`).**
  - **`IClang` (`include/fcpp-agent/IClang.h`) — ВСЕ обращения к libclang идут через этот виртуальный интерфейс** (запросы A–J). Application-код и прогрев кэша зависят только от `IClang`, никогда — от libclang напрямую.
  - **`CClang22` (`src/index/CClang22.{h,cpp}`) — реализация `IClang` под целевую версию clang 22** (дефолт, ADR-06). Добавление другой версии — новый класс (`CClangXX : public IClang`) без изменения core (§2.2, безболезненная версионность).
  - `ICompilerIndex` — **высокоуровневый** интерфейс графа отношений (DERIVED, по семействам D/E/G/I). Реализация **строит граф из SQLite**, а libclang (`IClang`) использует только для первичного наполнения/refresh. `dispatch_targets`/`included_by`/`derived_types` живут здесь, не в `IClang`.
  - `CClangVisitor` — RAII-обёртки над `CXIndex/CXTranslationUnit/CXString/токены` + обход AST (обязательный dispose); используется только внутри `CClang22`.
  - Разделение уровней: `IClang` = низкоуровневый «сырой» доступ к clang; `ICompilerIndex` = детерминированный граф из индекса. Прогрев кэша идёт через `IClang` (или через `ICompilerIndex`, который внутри вызывает `IClang`).
  - Фабрика `create_clang_backend(...)` возвращает `std::unique_ptr<IClang>` по конфигу (`tool_clang_path`/дефолт llvm22).

  **Плюсы `IClang` (принято):** (1) bypass libclang в тестах — подмена стабом; (2) версионная расширяемость без правок core; (3) единая точка RAII и изоляции crash-prone libclang (при желании — за `IndexWorker`-процессом).

  **Уточнение (моё предложение):** `IClang` действительно абстрагирует доступ к clang, но **граф отношений (callers/derived/overrides/dispatch) должен собираться один раз в SQLite и обслуживаться `ICompilerIndex`**, иначе каждый запрос tools снова пойдёт в libclang и вернётся зависимость от скорости clang (§3.3/§63). Т.е. `IClang` = «как читать clang», `ICompilerIndex` = «граф, из которого отвечают tools».

  **Удовлетворённые требования:** §15 (сущности), §36–40 (tools), §42–44 (compile/patch-verify), §21/§51 (cursor/Subject), §38 (overrides/inheritance).

  **Альтернатива:** собственная генерация AST через Clang LibTooling — мощнее, но тяжелее; libclang достаточно для read-only индекса MVP, а позже back-end абстракция (§2.2) позволяет добавить LibTooling без изменения application-кода.

* **Статус:** ⏳ На рассмотрении

### ADR-14: Минимальный контракт запроса `ask` в Agent API

* **Контекст:** Текущая реализация `ask` нарушает границу Agent API: клиент вынужден знать внутренние сущности ядра, а сам запрос собирается из argv в обход API.

* **Проблема (наблюдения):**
  1. `ask` **не является методом** `EApiMethod`; CLI `main.cpp` вызывает `CAskService` напрямую, минуя `CAgentApi` (нарушение §93 и §89.13).
  2. В клиентскую поверхность просочились внутренности: команда `route --area A --relation R --projection P` раскрывает `EArea`/`ERelation`/`EProjection` (запрещено §89.39/§90).
  3. `SApiRequest` перегружен полями, не относящимися к `ask` (`m_tool`, `m_target`, `m_payload`, `m_limit`, `m_assume_yes`, `m_build_after`).

* **Решение (принято):**
  - Клиент `ask` передаёт **только**:
    ```text
    text   — текст запроса
    editor — опциональный контекст: { file { path }, cursor { line, column } }
    ```
    Поля `file` и `cursor` необязательны; запрос обязан работать **без** них (§89.11).
  - Всё остальное — внутренности ядра: `Area`, `Relation`, `Projection`, `Subject`, `Tool`, `target`. Клиент их не отправляет и не знает.
  - `ask` становится методом `EApiMethod` (например, `EApiMethod::Ask`); CLI и IDE вызывают его через `CAgentApi::execute(SApiRequest)` (обязательно по §93).
  - `--stream` — режим вывода, а не свойство запроса; в API-тело не входит.
  - Команда `route --area/--relation/--projection` **удаляется** из клиентской поверхности (её роль — внутренняя отладка, не публичный контракт).
  - Внутри ядра вид (`m_kind`) по-прежнему определяется из текста (lite), а курсор лишь локализует сущность (см. ADR-13).

* **Удовлетворённые требования:** §89.11 (editor context), §89.12 (`session.update_context`), §89.13 (`ask`: text + editor), §89.39/§90 (API не раскрывает внутренние сущности), §93 (CLI — тонкий клиент).

* **Статус:** ✅ Принято

### ADR-13: Разрешение курсора — вид из фразы, имя из охватывающей сущности (§21)

* **Контекст:** Прогон `ask "Что делает этот класс?"` с курсором на `shape.hpp:25:15` (внутри `Shape::area`) дал неверный субъект: `FUNCTION Shape::area` вместо `CLASS Shape`.

* **Проблема (наблюдения):**
  1. Блок курсора в `CAskService::ask` безусловно перезаписывал `m_kind`, `m_name`, `m_selection` из **одного** innermost-символа.
  2. `CClang22::cursor_at` возвращает **ближайшую** сущность (метод), не поднимаясь до вида, заданного фразой.
  3. Эксперимент (закомментирована перезапись `m_kind`/`m_name`): `m_kind` от фразы сохранился (`CLASS`), но `m_name` остался догадкой lite (`shape`) и не нашёлся в индексе.

* **Решение (принято):**
  - **Вид (`m_kind`) задаёт пользовательская фраза** и никогда не затирается курсором (§20, §21).
  - **Курсор разрешает имя** как ближайшую **охватывающую** сущность **запрошенного вида**: «этот класс» → ближайший охватывающий класс (`Shape`), «эта функция» → ближайшая охватывающая функция (§21: «nearest enclosing class»).
  - Вызов `resolve_cursor` допустим **только когда имя не задано явно** (actuality: имя есть → курсор не нужен).
  - Lite-модель **не должна выдумывать имя** для дейктики («этот/эта/это»); при местоимении `name` оставлять пустым.
  - **Обобщение (ADR-19):** подъём курсора всегда **kind-directed** — до предка запрошенного `m_kind`, а не «до первого попавшегося». Случай «что делает этот класс?» с курсором на методе наследника — это **не декомпозиция**, а именно kind-directed резолв (§21).

* **Механика:** в слой `IClang` вводится уровень охвата (`Innermost|Type|Callable|Namespace`); `cursor_at` поднимается по семантическим родителям до первой сущности запрошенного вида. Fallback — ближайшая сущность (совместимость с прежним поведением).

* **Удовлетворённые требования:** §20 (Kind/Selection — разные измерения), §21 (детерминированный резолв, «ближайший охватывающий класс»), §51 (курсор — часть request context).

* **Статус:** ✅ Принято

### ADR-15: Живой benchmark и агрегатные/иерархические запросы

* **Контекст:** Запрос `ask "Все ли методы у наследников реализованы или есть заглушки?"` с курсором `circle.hpp:26:14` (метод `Circle::area`) вернул `NOT_UNDERSTOOD: no route for intent`.

* **Проблема (наблюдения):**
  1. **Промах классификации (LLM):** lite вернула `VERIFY / METHOD / REFERENCES / EXPLANATION`.
     - `VERIFY` — неверно: §19 определяет VERIFY как «выполнение проверок (build/tests)», а вопрос — о **состоянии кода** → корректно `UNDERSTAND`.
     - `REFERENCES` — неверно: смысл «реализованы/переопределены» ближе к `OVERRIDES`, а не к ссылкам.
     - `Subject METHOD` — сужение: вопрос про **все** методы **всех** наследников, а не про один `Circle::area`.
  2. **Дыра в таблице маршрутов:** маршрута `(Understand, References, Explanation)` не существует (для References есть только `Locations`) — даже при верной Area план был бы пуст.
  3. **Архитектурный пробел в Intent IR:** `Subject` описывает **единственный** объект (§20), но запрос **множественный и иерархический** («все наследники», «все методы»). Измерения `Area×Subject×Relation×Projection×Effect` не выражают агрегат/обход поддерева. Курсор при этом сужает иерархию до одной функции.
  4. Данные для ответа уже есть: инструменты `Overrides`, `Derived`, `Dispatch` (маршрут `(Understand, Overrides, Locations)`).

* **Решение (принято):**
  - Ввести **живой benchmark** как обязательный процесс развития классификатора (§71–72): каждый реальный промах → новый кейс в `tasks/benchmark.md` → regression.
  - Зафиксировать кейс `circle.hpp:26:14` в `tasks/benchmark.md` (ожидаемое: `UNDERSTAND`, Relation `OVERRIDES`, агрегат по наследникам).

* **Открытый вопрос (на рассмотрении): агрегатные/иерархические запросы.**
  - Вариант A: новое измерение `Quantifier/Scope` (`One | All | Derived`) — «для всех наследников».
  - Вариант B: новая `Relation::Hierarchy` либо трактовка `Subject=Type` как обхода поддерева `Derived`.
  - Вариант C: новая `Projection::Aggregate` (сводка по множеству).
  - Дополнительно: закрыть дыры в маршрутах (напр. `(Understand, References, Explanation)`).

* **Удовлетворённые требования:** §71 (структура benchmark), §72 (живой набор), §19 (area-таксономия), §23 (relation), §59 (видимая ошибка).

* **Статус:** ⏳ На рассмотрении (benchmark-процесс — принят)

* **Уточнение (принято):** причина B-002 — **не форма осей IR**, а отсутствие **декомпозиции/оркестрации** составного запроса (subtasks, §48/ADR-09). Варианты A/B/C отклонены как лечение симптома; см. ADR-16.

### ADR-16: Декомпозиция и оркестрация составного запроса (subtasks, §48)

* **Контекст:** Составные вопросы («Все ли методы у наследников реализованы?») не выражаются одной пятёркой осей Intent: они распадаются на цепочку простых под-запросов, каждый из которых **уже** поддержан существующими Relation/Tool. Проблема — в отсутствии механизма декомпозиции и передачи результатов между шагами. `allow_subtasks` (§48) до сих пор лишь feature flag.

* **Решение (принято):**
  - Ввести отдельный subsystem **subtasks**, не меняющий основной pipeline (§48, ADR-09).
  - **Режим M1 (MVP):** линейная цепочка под-задач; Evidence **накапливается** по шагам; финальный ответ формирует `main`-модель по объединённому Evidence.
  - Работает **над** однопроходным `ask`: оркестратор последовательно вызывает существующие примитивы (`CRequestPipeline::run_from_intent` + `CEvidenceCollector`) — по одному под-интенту за раз.
  - За флагом `allow_subtasks`: при `NO` поведение идентично текущему (однопроходному).

* **Слои:**
  - **Декомпозиция (lite):** составной запрос → упорядоченный список под-интентов (каждый — валидный `SIntent`).
  - **Валидация:** каждый под-интент обязан иметь route; иначе шаг → `NOT_UNDERSTOOD` (шаг виден, §59).
  - **Оркестрация (детерминированная, без LLM):** исполнение под-задач по порядку, накопление Evidence.
  - **Финал (main):** единый ответ по объединённому Evidence.

* **Инварианты/guardrails (closed security):**
  - Жёсткие лимиты: `max_subtasks`, `max_total_evidence`; порядок стабилен.
  - `depends_on` только на предыдущие шаги (ацикличность).
  - Новых осей/Relation/Projection/tools **не вводим**; множественность возникает **между** подзадачами, не внутри `Subject`.
  - Артефакты промежуточных шагов — conversation context (§49), не запись в проект/индекс.

* **Связь со спецификацией:** §48 (отдельный subsystem, `allow_subtasks`), ADR-09 (snapshot, наружу только Evidence), §49–§50 (conversation context, приоритет источников), §59 (ошибка видна), §89.13 (контракт `ask` не меняется).

* **Отложено (не MVP):** режим **M2** — map с подстановкой артефакта (`{derived}`) и reducer-вердиктом; ветвление цепочек.

* **Уточнение (ADR-19):** декомпозиция — **последнее средство**, а не первый ответ. Мультипликативность «один Subject → N целей» (напр. «добавь метод в интерфейс и реализуй в наследниках») решается **fan-out в Planner** (ADR-19), без LLM. Декомпозиция оправдана только при детерминированном триггере (§64 бюджет / порядковая зависимость).

* **Статус:** ✅ Принято (M1); M2 — отложено

### ADR-17: Двухфазная декомпозиция (структура — lite, семантика — ядро)

* **Контекст:** Нужен механизм разложения составного запроса на вектор под-интентов, исполняемый единым dataflow (ADR-16). Эксперимент показал: lite хорошо выделяет атомарные подвопросы, но **теряет anchor** (вместо «этот класс» обобщает до «базовые классы проекта») и легко выходит за выразимые примитивы.

* **Решение (принято) — две фазы:**
  - **Фаза A (lite):** только **структура** — составной запрос → упорядоченный список подвопросов **на естественном языке** (не enum).
  - **Фаза B (ядро):** каждый подвопрос отдельно проходит существующий `CIntentAnalyzer` (с эскалацией ADR-10) → `SIntent`; валидируется наличие route.

* **Правила промпта Фазы A:**
  1. Атомарность: один подвопрос = один факт из индекса (несколько пунктов внутри — разворачивать).
  2. **Сохранять anchor**: курсор/субъект подставлять дословно; запрет обобщать («этот класс» ≠ «проект»).
  3. Если запрос атомарный — вернуть ровно один подвопрос.
  4. Лимит N и требование порядка (найти множество → проверить предикат → inspect тела).
  5. Опираться на выразимые Relation/Projection (перечислять их в промпте).

* **Валидация (ядро):** подвопрос, чей `SIntent` не имеет route, отбрасывается с явной пометкой (§59). Вердикт («все ли реализованы») — не подвопрос, а **финал** по union-Evidence.

* **Классификация подвопросов эксперимента:**
  - выразимо сейчас: базовые типы с virtual, наследники, virtual/=0 методы, override-полнота;
  - частично: заглушки (тело) — `Projection::Source` + анализ текста тела;
  - невыразимо сейчас (`[[deprecated]]`/`=delete`/`=default`, покрытие тестами) — отбрасывать с пометкой в MVP; при необходимости позже ввести Relation/Tool.

* **Глубина:** плоский список (глубина 1). Рекурсия/вложенность — не MVP (M2).

* **Связь со спецификацией:** ADR-16 (вектор/нить), ADR-10 (эскалация Intent), §25 (маленькая таксономия), §59 (видимая ошибка шага).

* **Уточнение (ADR-19):** **вектор — инвариант** анализа запроса: он всегда вектор, в нём либо один входной запрос, либо несколько атомов. Composer — **один системный промпт, один вызов**, который либо возвращает список атомов, либо отдаёт запрос как есть. Декомпозиция — last resort (см. ADR-16).

* **Статус:** ✅ Принято

### ADR-18: Качество декомпозиции — якорь, классификация, резолв (план фиксов B-002)

* **Контекст:** Прогон B-002 после реализации двухфазной декомпозиции (ADR-17) дал видимые сбои: подвопросы привязались к `Circle` вместо базового `Shape`; `DESIGN`/`SIGNATURE`/`REFERENCES` вместо `UNDERSTAND`/`OVERRIDES`; ложный `CLARIFY` (`Circle` vs `Circle::Circle`); отсутствие маршрута под просмотр тел.

* **Список фиксов (по приоритету; №0–2 — блокирующие):**
  1. **№0 Якорь Фазы A (навигация по иерархии через clang).** Якорь — это **детерминированная достижимость базового класса**, а не свойство методов (`virtual`/`=0` здесь НЕ критерий: базовый класс может не иметь ни одного чисто виртуального метода, а `=0` — признак абстрактности, а не принадлежности к иерархии).
     - **Вход:** курсорная сущность (класс).
     - **Действие:** спросить у clang/индекса, есть ли базовый класс и достижим ли он — подъём по цепочке наследования через `base_types(USR)` / `ancestors(USR)` (ADR-11) либо по `parent_usr`.
     - **Результат:** достижимо → якорь = базовый класс; недостижимо (нет данных/вне индекса) → якорь = курсорная сущность либо уточнение §22.
     - **Множественное наследование:** баз может быть несколько → якорь — множество (или корень иерархии).
     - **Условие применения:** подъём к базе — только для вопросов про иерархию/переопределения; для «этот класс» — без автоподъёма.
     - В промпт Фазы A детерминированно подставлять имена охватывающего класса курсора и его баз (из индекса), чтобы lite не угадывал.
     - **Пред-требование:** прямой `base_types`/`ancestors` в `IClang` сейчас — задел (реализованы только `extract` + `cursor_at`); до его появления допустим подъём по `parent_usr`.
  2. **№1 Классификация Фазы B.** В промпт `CIntentAnalyzer` добавить правила: `реализован|override|заглушк|переопределён → OVERRIDES`; вопросы о состоянии кода → `UNDERSTAND` (`VERIFY`/`DESIGN` — только build/tests и проектирование). Плюс **детерминированная пост-коррекция** (Секция 3): `References → Overrides` при ключевых словах; `Design → Understand`.
  3. **№2 Маршрут под тела.** Добавить маршрут `(Understand, Overrides, Source) → {Overrides, Dispatch, Source}`, иначе «посмотреть реализацию/заглушку» невозможно.
  4. **№3 Фильтр по `Subject.kind` в резолвере.** `resolve_subject` учитывает `intent.m_subject.m_kind` (для `CLASS` — только class/struct) — убирает ложный `CLARIFY` (§20).
  5. **№4 Промпт финала.** Требовать таблицу-вердикт «наследник × метод → реализован/заглушка/нет».

* **Связанный процесс:** кейс B-002 в `tasks/benchmark.md` — остаётся FAIL до закрытия №0–2.

* **Связь со спецификацией:** ADR-17 (декомпозиция), §19 (area-таксономия), §20–21 (Subject/резолв), §23 (relation), §24 (projection), §30–31 (детерминированный план), §59 (видимая ошибка).

* **Статус:** ✅ Принято (план); реализация — далее

### ADR-19: Fan-out Subject → N как детерминированный разворот плана (§21/§31)

* **Контекст:** Часть запросов — не семантическая декомпозиция, а **структурная операция над графом наследования**: один Subject → множество целей (например, «добавь метод в интерфейс и реализуй в наследниках», «все ли методы у наследников реализованы»). Это не требует LLM-стадии.

* **Решение (принято):**
  - Planner **детерминированно** разворачивает один Subject в N целей через `derived_types()` / `dispatch_targets()` (`ICompilerIndex`, Этап 4) — §21/§31: «LLM не ищет сама, резолвит core».
  - Fan-out живёт в **deterministic core**, а не в subtasks; §48 (subtasks не меняют pipeline) не затрагивается.
  - **Два режима:**
    - **read-fan-out** (UNDERSTAND/REVIEW): N целей → **union** Evidence (порядок не важен);
    - **write-fan-out** (CHANGE): N целей → **упорядоченные** изменения (порядок — часть семантики: «спроектировать интерфейс» до «реализовать в наследниках»).
  - **Reduce обязателен:** мультипликативность (composer ИЛИ fan-out) всегда завершается стадией сведения (union или ordered).
  - Мультипликативность **вкладывается**: атом из composer сам может fan-out'иться (два уровня).
  - **Якорь** для fan-out определяется навигацией к базовому классу через clang (ADR-18, №0), а не свойствами методов.

* **Разграничение механизмов (важно):**
  - **kind-directed резолв** (ADR-13): курсор → предок нужного `m_kind`. Не декомпозиция.
  - **fan-out** (настоящий ADR): Subject → N целей по Relation/иерархии. Не декомпозиция, LLM не нужен.
  - **декомпозиция** (ADR-16/17): last resort при триггере §64/порядок.

* **Связь со спецификацией:** §21 (Subject Resolution), §31 (детерминированный план), §23 (Relation), ADR-11 (`derived_types`/`dispatch_targets`), ADR-13, ADR-18.

* **Статус:** ✅ Принято (план); реализация — далее

### ADR-20: Символ под курсором передаётся lite как готовый хинт (B2)

* **Контекст:** Прогон «как считается возвращаемое значение?» с курсором на `Rectangle::area` дал субъект `Shape` (уход к базовому классу). Причина: lite не видит символ под курсором (ей передавалась лишь координата `file:line`), оставляла `name=""`, после чего срабатывала безусловная подстановка якоря иерархии (`Rectangle → Shape`).

* **Решение (принято):**
  - **Если курсор есть** — детерминированно резолвить символ под ним через `IClang::cursor_at` (innermost) и передавать lite **готовый хинт** `[cursor symbol: NAME (KIND)]`.
  - **Применимость решает сама lite:** если вопрос про этот символ — `subject = NAME`, `selection=CURSOR`; если вопрос общий/проектный — хинт игнорируется.
  - **Разведение хинтов:** Фаза A (декомпозиция) получает `[hierarchy anchor: …]` (иерархический контекст); Фаза B (Intent) в **одиночном** режиме получает `[cursor symbol: …]`; в **составном** режиме хинт не подаётся (подвопросы самодостаточны), при пустом имени подставляется якорь.
  - Удалены ad-hoc `is_deictic` и `resolve_cursor` по виду — их роль выполняет lite, видя символ.

* **Обоснование:** §21 («LLM не ищет сама, резолвит core»): core резолвит позицию в символ; применяемость — задача интерпретации, где lite сильнее эвристики.

* **Связь:** ADR-13 (kind-directed), ADR-18 №0 (якорь иерархии), §51 (курсор — часть request context).

* **Статус:** ✅ Принято; B-003 (простой) — PASS, B-002 (составной) — PASS.

### ADR-21: Граница клиента — только text + file? + cursor?

* **Контекст:** Обсуждение интеграции IDE/плагина. Плагин «не знает» внутренних сущностей, но вопрос в том, что именно составляет **клиентское знание**.

* **Решение (принято):**
  - Клиент (IDE/плагин/CLI) знает и передаёт **только**:
    ```text
    text    — текст запроса (всегда)
    file    — файл (опционально; может отсутствовать, напр. IDE только открыта)
    cursor  — позиция (опционально; осмысленна только вместе с file)
    ```
  - Всё остальное (`session_id`, `project_id`, `request_id`, события `request.*`/`index.*`, состояния) — **прозрачная маршрутизация агента**, а не знание плагина.
  - Случаи: нет `file` → вопрос общий (контекст из индекса проекта); есть `file` без `cursor` → вопрос про файл; есть `file`+`cursor` → вопрос про точку (B2).

* **Уточняет:** §94 / ADR-14 — фиксируется как **единственное обязательное знание** IDE.

* **Связь:** §89.11 (editor context необязателен), §89.13 (`ask` = text + editor), §41 (transport independence), §89.39 (граница API).

* **Статус:** ✅ Принято

### ADR-22: Позиционный резолв над индексом — метод `symbol_at` в `ICompilerIndex`

* **Контекст (дыра):** Кучу сил вложено в индекс-кэш (`symbol_location` в `index.db`), прогреваем на больших и малых проектах, но позиционный резолв курсора всё равно идёт в `IClang::cursor_at` — то есть перепарсивает TU и дублирует то, что уже посчитано. Для dogfood незаметно; на реальном проекте — лишние парсинги в hot-path.

* **Решение (принято, Вариант A):**
  - Добавить метод в **`ICompilerIndex`** (реализация `CSqlCompilerIndex`):
    ```cpp
    std::optional<SSymbol> symbol_at(const std::string& file, std::uint32_t line, std::uint32_t column) const;
    ```
  - Реализация — над `index.db`: `file` → `file_id` (через существующий `find_file_id`), затем `SELECT` по `symbol_location` с выбором **наиболее вложенной** сущности (минимальный диапазон; метод побеждает класс).
  - **Fallback — `IClang::cursor_at`**, когда: файл вне индекса, сущности в диапазоне нет, или файл помечен stale.
  - `CAskService` и другие потребители спрашивают `ICompilerIndex::symbol_at`, а не clang напрямую.

* **Политика приоритета (обязательна, иначе недетерминизм):**
  - файл **свежий** (hash/mtime совпадают с индексом) → доверяем **кэшу** (`symbol_at`);
  - файл **stale** (изменился после индексации) → доверяем **clang** и инициируем точечный refresh (ADR-05);
  - **неполнота** индекса (промах по диапазону) → clang-innermost.

* **Размещение:** запрос — в `ICompilerIndex`/`CSqlCompilerIndex` (рядом с уже имеющимися `derived_types`/`ancestors`); `IClang` остаётся сырым доступом к clang и **не читает БД** (ADR-11).

* **Обоснование выбора A:** минимум новых типов — один метод в уже существующем интерфейсе; `ICompilerIndex` и так обслуживает все запросы из SQLite (§3.3), а `symbol_location` — это индексная таблица. Отдельный `IPositionResolver` (вариант B) избыточен, пока потребитель один.

* **Отклонено:** декоратор `CCachedClang : public IClang` (прячет БД под именем clang — нарушает ADR-11); отдельный `IPositionResolver` (вариант B) — избыточная сущность при одном потребителе.

* **Связь:** §3.3 (SQLite — основной источник индексированного контекста), §15/§17 (индекс, актуальность), ADR-11 (разделение IClang/ICompilerIndex), ADR-05 (stale), ADR-20 (потребитель — cursor_symbol).

* **Статус:** ✅ Принято (план); реализация — далее

### ADR-23: LLM-driven loop (ReAct) поверх детерминированных tools

* **Контекст:** Предзаданный детерминированный путь (`Intent → planner → Evidence`) не выдерживает сложные/неоднозначные вопросы: разбор делается заранее, без итерации. Эксперимент показал, что локальная `Qwen2.5-Coder-14B` нативно поддерживает `tools`/`tool_calls` и ведёт многошаговый диалог (`derived → outline → source`).

* **Решение (принято):**
  - Модель **ведёт цикл**: решает, какой инструмент вызвать, видит результат, продолжает до ответа.
  - Инструменты исполняет **детерминированный core** (`CToolRegistry`), срезы Zero-Window.
  - `CReActAgent`: цикл `complete(messages, tools) → tool_calls → execute → результат → …`.
  - Схемы инструментов и формат результата — из `EToolName` (`tool_schemas`/`format_tool_result`).
  - **Guardrails:** `max_steps`, валидация JSON-аргументов, ошибка возвращается в диалог; шаги логируются в stderr.
  - Режим включается в конфиге: `react_loop` (дефолт **YES**), `loop_model` (`main|light|remote`).
  - Детерминированный пайплайн (`Intent/planner/Evidence`) остаётся **fast-path/fallback**.
  - Контекст курсора передаётся в loop (`[cursor symbol: NAME (KIND)]` + якорь иерархии).

* **Протокол:** единый `IModelApi` (абстракция tool-calling); провайдер транслирует в свой native-формат (OpenAICompat/Claude) — не требование к моделям.

* **Связь:** ADR-10 (каскад), ADR-20 (курсор), ADR-22, §41 (транспорт), §56/§63 (Zero-Window).

* **Статус:** ✅ Принято; E2E пройден (простой и сложный сценарии).

### ADR-24: Роутинг моделей — изолированные контексты + handoff (planner/worker)

* **Контекст:** Нужно экономить на дорогих (cloud) моделях, отдавая им только сложное, а простое — локальной. Предсказание «сложности» и «оптимальности» ненадёжно (самооценка модели, классификатор — гадание; «suboptimal» непроверяем).

* **Решение (принято):**
  - **Не стравливать логи.** Паттерн **B**: у local и cloud **изолированные контексты** (`messages`); между ними передаётся не лог, а **структурированный handoff-пакет**.
  - **Handoff-пакет:** `goal`, `resolved_subjects` (USR), `metrics` (blast radius), `facts[]` (срезы), `open_questions[]`; обратно — `план шагов`.
  - **Роли:** local — **разведчик + исполнитель** (резолв субъекта, метрики из индекса, вызовы tools); cloud — **планировщик/синтез** для крупных шагов.
  - **Разведка до роутинга:** первые дешёвые local-шаги дают объективные метрики — роутим по **измеренному** радиусу, а не по предсказанию.
  - **Blast radius — детерминированно из индекса** (без LLM): #files в include-подграфе, размер derived-closure, #callers/refs, глубина иерархии, `EEffect` (Read/Write/Exec).
  - **Детект сложного** — лексика+структура (глаголы изменения: рефактори/переименуй/раздели; множественность: «во всех», «везде»; крупный агрегат: «микрофреймворк»; широкая проекция: Graph).
  - **Простое** определяется **собственными признаками** (тип шага, Read, малый радиус), а не инверсией сложности (иначе попадут невалидные/CLARIFY).
  - **Переключение — только между раундами** (не внутри), чтобы история оставалась валидной (у каждого `tool_call` есть парный результат).
  - **Бюджет cloud** (расширение ADR-10) + **sticky**: раз cloud начал планировать — доводит план; затем эстафета local.
  - **Аудит:** каждый раунд тегируется, кто его произвёл (`local|cloud`).
  - **Человек в контуре:** ручной `--escalate`; авто-эскалация — только на **объективном** провале (compile/tests/evidence/AMBIGUOUS).

* **Отклонено:** предсказание сложности самооценкой модели как гейт; плоское чередование на общей истории (шум/токены).

* **Связь:** ADR-10 (каскад/бюджет), ADR-23 (loop), §6/§7 (роли моделей), §49 (conversation context), §64 (бюджет).

* **Статус:** ✅ Принято (план); реализация — **не начата** (актуальный статус и связь с conversation context: см. ADR-27).

### ADR-25: Эскалация модели внутри ReAct-loop (каскад сбоя)

* **Контекст:** Прогон на реальном проекте: локальная модель прошла `search → source`, но на шаге, где `source` вернул абстрактный метод (`virtual void onTick() = 0;`), ответила **пусто** (`finish=stop`, без `tool_calls`, `content=""`). Эксперимент: та же история с подсказкой «продолжай» → модель корректно вызвала `overrides(CTimer::onTick)`. То есть **пустой ответ — не «финал», а признак того, что модель не справилась** (сдалась).

* **Решение (принято):**
  - **Пустой ответ = триггер эскалации** (не финал). Это не «модель закончила», а «модель не справилась» — наблюдаемый, объективный сигнал (в духе ADR-10).
  - **Эскалация внутри loop**: при срабатывании триггера `CReActAgent` меняет `IModelApi*` на **следующий уровень** (`main → remote`, либо `light → main → remote`) и **продолжает цикл на ТОЙ ЖЕ истории** (`messages`) — контекст уже собран, handoff бесплатен.
  - **Триггеры (детерминированные):**
    1. `EmptyReply` — `finish=stop`, нет `tool_calls`, пустой `content`;
    2. `Loop` — однотипный повтор вызова N раз;
    3. неразрешённый `AMBIGUOUS` за N шагов;
    4. приближение к `max_steps`.
  - **`EGlitchKind::EmptyReply`** — новый тип глюка (пустой ответ модели).
  - **Бюджет** (расширение ADR-10): лимит эскалаций на запрос, hard-stop; **sticky** — раз эскалировали, держимся уровня до конца запроса.
  - **`loop_model`** задаёт **стартовую** (дешёвую) модель; эскалация повышает её.
  - **nudge не нужен** — он заменён эскалацией (подталкивать слабую модель — лечение симптома).
  - **Config-collapse (уточнение):** уровни строятся только для доступных и **различных по endpoint** ролей. При `model_light="same_as_main"` уровни `light` и `main` указывают на один физический сервер — это НЕ эскалация, их надо схлопнуть. Тогда при недоступности `light` (или совпадении с `main`) эскалация идёт **сразу на `remote`**; а если `remote` не настроен — loop **честно признаёт неуспех** («модель не справилась, более мощная не настроена, уточните вопрос»), а НЕ выдаёт сырую гипотезу и НЕ падает в детерминированный fast-path.
  - **Диагностические вопросы (уточнение):** для вопросов вида «почему так» запрещено финализировать гипотезой («возможно/вероятно»). Промт loop обязывает прочитать код, выполняющий соответствующую логику (`source` точных символов и вызываемых ими функций), и назвать **конкретную, подтверждённую** причину.

* **Разведение (важно):**
  - **Эскалация-каскад** (этот ADR): **общая история** `messages`, смена модели при сбое — допустимо (это каскад сбоя ADR-10).
  - **Planner/worker** (ADR-24): **изолированные контексты** + handoff-пакет — для разделения труда (cloud планирует, local исполняет).
  - Это два разных механизма; смешивать нельзя.

  - **Наблюдённые классы сбоя (уточнение):** на реальном `reminder` модель последовательно выдавала: (а) **пустой ответ**; (б) **«сломанный» текстовый вызов** — JSON-массив/code-fence вместо нативного `tool_calls`; (в) **«наррацию плана»** — «давайте посмотрим…», «теперь проверим…» без вызова tool и без ответа; (г) **«сдачу»** — извинение/просьбу поправить (в т.ч. после выдуманного пути вроде `path/to/CEventsSyncTimer.h`). Всё это — непроизводительные ответы (класс `EMPTY_REPLY`), детектируются эвристиками (`looks_like_tool_call_text`: ключи `arguments`/`function`+`name`, `` ```json ``, незакрытый `` ``` ``; `looks_like_plan_narration`: маркеры плана при отсутствии маркеров вывода; `looks_like_give_up`: извинения/«пожалуйста, убедитесь») и ведут к эскалации, а НЕ принимаются за финал. Промт дополнительно запрещает выдумывать пути/имена и требует использовать только имена, возвращённые tools.
  - **Нормализация аргумента-имени:** модель часто передаёт C++-выражение (`m_eventsNodes->trackedDatesNodes()`, `obj.field`, `Foo::bar()`) — [`normalize_symbol_target()`](src/core/CReActAgent.cpp:97) снимает `()`, `->`, `.` до имени символа (иначе `source(...)` падал в `SymbolNotFound` и сжигал шаги).
  - **Анти-цикл:** повтор вызова по нормализованному имени помечается в тексте tool-результата (note «do not repeat»).
  - **Приоритет вердикта:** настоящий финальный ответ (текст есть, tool_calls нет, признаков сбоя нет) принимается ДО проверок на сбой — чтобы не зацикливаться, если сильная модель дала корректный ответ, содержащий слово из маркеров плана.
  - **Бюджет `max_steps` = триггер.** При исчерпании шагов — сначала эскалация на более мощный уровень, затем **принудительный финальный синтез** ответа по уже собранной истории (без tools) с требованием конкретики из прочитанного кода. Сырая гипотеза не сбрасывается, падение в детерминированный fast-path не происходит.

* **Связь:** ADR-10 (каскад/триггеры/бюджет), ADR-23 (loop), ADR-24 (роутинг), §6/§7 (роли), `EGlitchKind`.

* **Статус:** ✅ Принято; реализовано (config-collapse уровней; эскалация EmptyReply/BrokenToolCall/PlanNarration/GiveUp/budget; нормализация имён; анти-цикл; финальный синтез по истории). Проверено на `reminder`:
  - с курсором (текст БЕЗ имени метода) — `cursor_symbol` вернул `CEventsSyncTimer::onTick`, loop сразу вызвал `source(...)`; метод определился автоматически (§95: клиент шлёт text + editor{file,cursor});
  - `PLAN_NARRATION → remote` и финальный синтез дали конкретный ответ: `onTick` по дате не фильтрует; задержку задают `period_ms` (`CTimer::start → m_queue->submit`) и хранимая процедура `refresh_tracked_nodes`.

### ADR-26: Закрытие незавершённых ветвей dataflow запроса (заглушки)

* **Контекст:** Обход всех ветвлений dataflow `ask` выявил незакрытые/заглушечные ветви. Часть — мёртвый код, часть — реальные обрывы цепочки.

* **Найдено и реализовано:**
  1. **`include → source` (обрыв dataflow).** `include` возвращал лишь имена файлов; получатель включения не читался. Теперь в [`CReActAgent`](src/core/CReActAgent.cpp:1) после успешного `include` детерминированно подтягивается `source` первых `k_max_include_follow=3` получателей (глубина 1, анти-дубль через `followed_files`).
  2. **`budget exhausted` терял факты.** При исчерпании `max_steps` и отсутствии финального текста ответ сбрасывался в `false`. Теперь возвращаются собранные результаты инструментов (`gather facts`), без «пустой заглушки». `max_steps` поднят 14→20.
  3. **`CModelClaude::complete(messages, tools)` — заглушка (`(void)tools`).** Реализован полноценный Claude `tool_use`: схемы в `tools` (`input_schema`), `tool_calls` парсятся из `content[]` (`type=tool_use`), assistant-сообщения с вызовами и `tool_result`-блоки корректно сериализуются. Claude теперь пригоден как ведущая модель ReAct.
  4. **Протокол `serve` регистрировал лишь 12 из 16 методов API.** Добавлены `config.reload`, `project.list`, `tool`, `patch`, `build.build`, `tests.run`; парсятся `tool/target/payload/limit/assumeYes/buildAfter/stream`. `serialize_response` теперь отдаёт `names`/`locations`/`symbols`/`text` (раньше `tool` возвращал «пусто»).
  5. **`symbol_at` (ADR-22) — спроектирован, но не реализован.** Реализован в [`CSqlCompilerIndex`](src/index/CSqlCompilerIndex.cpp:292) (самая внутренняя сущность, чей `symbol_location` диапазон содержит позицию). `CAskService::cursor_symbol` переведён на **cache-first** (ADR-22): сначала `symbol_at` над индексом, fallback — `IClang::cursor_at`.

* **Осознанно не менялось:**
  - **`CSubtaskOrchestrator` не подключён.** Это дублирующая мёртвая реализация: `SSubTask` несёт только текст, а `run` ожидает уже собранный `SIntent`. Живой цикл (Фазы B+dataflow) реализован inline в [`CAskService::ask()`](src/core/CAskService.cpp:340) и протестирован. Форсировать оркестратор — рефактор без функциональной пользы и с риском регресса.
  - **Маршруты `CRequestPipeline`** — неисчерпывающее покрытие (некоторые area×relation×projection не имеют маршрута → `no route for intent`); это не заглушка, а задокументированная закрытая модель (неразрешённое → видимый отказ).

* **Проверка:** сборка успешна; CTest 47/47.

* **Связь:** ADR-22 (symbol_at), ADR-23/25 (loop), ADR-16/17 (subtasks), §89.7 (API surface).

### ADR-27: Модель роутинга и Conversation Context — статус (недоделки)

* **Контекст:** Продуктовая цель — «простая задача → локальная модель, сложная задача → облачная». В коде реализован только **один** механизм (эскалация по сбою, ADR-25), а заявленный роутинг «сложное — облаку, простое — локально» (ADR-24) остаётся **планом**. Отдельно отсутствует **conversation context** (§49/§50), что напрямую блокирует сценарий planner(cloud)/worker(local).

* **Недоделка 1 — роутинг planner/worker (ADR-24) не реализован.**
  - **Что есть:** `CReActAgent` стартует на роли `loop_model` и **эскалирует по объективному сбою** (пустой/сломанный/наррация/сдача/бюджет) на следующий уровень (ADR-25). Это **каскад сбоя одной и той же истории**, а не разделение труда.
  - **Чего нет:** (а) детерминированного расчёта **blast radius** из индекса (размер include-подграфа, derived-closure, #callers/refs, глубина иерархии, `EEffect`); (б) **роутинга по измеренному радиусу**; (в) **handoff-пакета** между изолированными контекстами (`goal`/`resolved_subjects`/`metrics`/`facts[]`/`open_questions[]` ↔ `план шагов`); (г) переключения **между раундами** со sticky-планировщиком и тегированием раунда (`local|cloud`); (д) бюджета cloud.
  - **Ограничение без контекста:** «простой» шаг нельзя безопасно отдать локальной модели в отрыве — у неё нет истории раунда. Это и есть связь с Недоделкой 2.
  - **Статус:** план (ADR-24), реализации нет.

* **Недоделка 2 — Conversation Context (§49/§50) отсутствует.**
  - **Что есть:** каждый `ask` строит `messages` заново (system + user + cursor-хинт). История живёт только внутри одного вызова loop'а.
  - **Чего нет:** (а) `session_id` в контракте `ask`; (б) методов `session.open`/`session.close`/`session.update_context` (§89.10, §89.12) — их нет в `EApiMethod`; (в) хранилища диалога и его сериализации в протоколе; (г) приоритезации источников при конфликте (§50: explicit → conversation → cursor/file → project → index → build).
  - **Важно:** `save_session`/`restore_session` в `CProjectManager` относятся к **проекту**, не к диалогу — это не conversation context.
  - **Статус:** «дыра» — не реализовано вовсе.

* **Взаимосвязь:** Недоделка 1 **зависит** от Недоделки 2: planner/worker с изолированными контекстами требует переносимого состояния диалога между раундами. Порядок закрытия: сначала §49 (conversation context) — базис; затем §7/ADR-24 (роутинг + blast radius + handoff).

* **Инварианты (не нарушать при реализации):**
  - Conversation context **не заменяет** project index (что обсуждает пользователь ≠ что есть в проекте) — §49.
  - Эскалация-каскад (ADR-25) и planner/worker (ADR-24) — **разные** механизмы; смешивать общую историю и изолированные контексты нельзя.
  - Переключение моделей — **только между раундами**, чтобы у каждого `tool_call` был парный результат.
  - «Простое» определяется собственными признаками (тип шага, Read, малый радиус), а не инверсией «сложности» (иначе в локальную ветвь попадут CLARIFY/невалидные).

* **Связь:** §7 (Model routing), §49/§50 (conversation context / hierarchy), §89.10/§89.12 (session API), ADR-10 (каскад), ADR-24 (план роутинга), ADR-25 (эскалация).

* **Статус:** 📝 Зафиксировано (недоделки + порядок закрытия). Реализация — далее.

### ADR-28: Conversation Context и Context Budget Manager

* **Статус:** ✅ Архитектурное решение принято; реализация ещё не выполнена.
* **Контекст:** История ReAct сейчас живёт в локальном `messages` одного `run`. Для длинных диалогов нельзя ни бесконечно добавлять сообщения в prompt, ни безвозвратно выкидывать старые сообщения по принципу round-buffer. §49/§50 требуют отдельного conversation context и явной иерархии источников; §64 требует управляемого бюджета контекста.
* **Решение:** Ввести `CContextManager` как компонент **сборки контекста конкретного вызова модели**, а не как синоним истории и не как LLM-резюматор «на глаз». Он выбирает и упорядочивает нужные сведения под текущий шаг ReAct, соблюдая бюджет токенов и обязательные инварианты. Полная история и компактное состояние сессии — отдельные сущности.

#### 1. Разделение ответственности

1. **Conversation store** — долговременная история событий сессии: user/assistant messages, tool calls, tool results, model/round metadata и timestamps. Записи добавляются, а не переписываются при compaction. История не целиком передаётся модели по умолчанию.
2. **Conversation state** — актуальная структурированная проекция сессии: текущая цель, пользовательские ограничения, подтверждённые факты, принятые решения, открытые вопросы, завершённые подзадачи и ссылки на доказательства. Для каждого факта хранить provenance (event/tool/source reference), статус и, где применимо, актуальность.
3. **`CContextManager`** — строит `SModelMessage`/prompt для одного вызова: выбирает обязательный контекст, релевантные evidence и недавние группы сообщений; учитывает модельный лимит; выполняет/запрашивает compaction, если нужно; возвращает диагностические метрики бюджета.
4. **Model adapter** — предоставляет известный context-window limit и, по возможности, точный token counter для конкретной модели/формата. Подсчёт по байтам или `sizeof(std::string)` не является бюджетированием токенов.
5. **`CReActAgent`** — управляет циклом reasoning/tool calls, но не реализует собственные правила усечения истории. Перед каждым обращением к модели запрашивает готовый контекст у `CContextManager`.

#### 2. Хранение

* Полная история диалога хранится отдельно от project index. Не записывать историю, prompt или tool output в `index.db`: это сохраняет смысл запрета ADR-02 и отделяет индекс проекта от пользовательских сессий.
* Для первой реализации использовать отдельное session store (SQLite в каталоге данных агента, например `~/.fcpp-agent/sessions/`); конкретные таблицы и миграции фиксировать в отдельном ADR/схемном решении после проверки существующей инфраструктуры сессий.
* Compaction не удаляет историю и не заменяет её summary. Summary — производная проекция, которую можно пересобрать из событий. При расхождении summary и первичных событий приоритет у первичных событий и подтверждённых evidence.
* Не сохранять секреты в контекст/логи вопреки ADR-08 и §61; применять существующую политику редактирования секретов до персистенции и передачи модели.

#### 3. Бюджет и сборка контекста

* Бюджет задаётся в **токенах на конкретную модель**, а не в байтах и не условным лимитом 1 GiB. Лимит окна берётся из конфигурации/адаптера модели; если он неизвестен, используется явный консервативный configured limit, а не бесконечный режим.
* Из общего окна резервировать место для ответа модели и служебного overhead формата/tool calls. Начальный порог compaction — при достижении 80% доступного prompt-бюджета; значение конфигурируемое. Это стартовый default для проверки тестами, не универсальная константа.
* Сборка выполняется в стабильном порядке для совместимости с prompt cache:
  1. неизменяемые system/policy instructions;
  2. текущий запрос и явные пользовательские ограничения;
  3. минимальное состояние задачи (цель, решения, открытые вопросы);
  4. обязательный контекст сессии и актуальный editor context, если он задан;
  5. evidence, выбранные под конкретную цель/инструментальный шаг;
  6. недавние сообщения и результаты инструментов, добавляемые целыми группами.
* Каждый кандидат оценивается детерминированно по категориям: обязательность/безопасность, прямое отношение к текущей цели, актуальность, доказательная ценность и стоимость токенов. Первые реализации используют явные правила и стабильный tie-break (время/ID), а не дополнительный LLM-вызов для каждого отбора.
* При переполнении сначала удаляются дубли и устаревшие низкоприоритетные детали; затем сокращаются большие tool outputs до релевантных фрагментов с сохранением ссылок на исходное событие/файл/строки; затем завершённые ветви заменяются компактным summary с evidence refs; затем отбрасываются наименее релевантные необязательные группы истории. Нельзя молча отбрасывать обязательные ограничения или незакрытые вопросы.
* Сообщения `assistant tool_call` и соответствующие `tool_result` — атомарная группа: при включении/исключении сохранять пару целиком. Аналогично не разрывать протокольные блоки конкретного provider.
* Summary явно разделяет **подтверждённые факты**, **предположения модели** и **нерешённые вопросы**. Предположения не повышаются до фактов без evidence. Каждый факт, который может повлиять на решение/изменение кода, должен сохранять provenance.
* Если обязательный контекст вместе с резервом ответа не помещается даже после compaction, завершать операцию явной типизированной ошибкой/диагностикой или запрашивать уточнение; не удалять обязательные данные и не повторять compaction бесконечно.

#### 4. Иерархия источников и конфликты

Сохранять приоритет §50: explicit user request > current conversation context > cursor/current file > current project > indexed project information > filesystem/build information. Внутри conversation state более новое явное исправление пользователя supersedes предыдущее. Индексные/инструментальные сведения должны хранить источник и поколение индекса; при устаревании их требуется перепроверять. История разговора не является доказательством текущего состояния исходников.

#### 5. Контракт и тестируемость

* Предусмотреть интерфейс вроде `build_context(request, session_state, recent_events, model_limits) -> SContextBuildResult`, где результат содержит сообщения, оценку/фактический token count, использованный бюджет, решение compaction и диагностические причины исключения кандидатов. Точные имена DTO можно адаптировать к текущему C++ стилю.
* `CContextManager` должен быть тестируемым без реальной LLM и без файловой системы: фиксированный token counter, synthetic event stream, заданные бюджеты.
* Обязательные тесты: контекст не превышает бюджет; обязательные инструкции/ограничения остаются; tool call/result не разрываются; релевантное evidence выигрывает у нерелевантной старой истории; summary сохраняет provenance и отделяет предположения от фактов; повторная сборка даёт стабильный порядок; неизвестный лимит не превращается в unlimited; обязательный контекст, который невозможно уместить, даёт явную ошибку.
* Метрики для диагностики: лимит окна, оценка токенов prompt, резерв ответа, токены по секциям, число включённых/исключённых событий, число compaction, причина compaction и факт достижения hard limit. Не логировать содержимое секретов.

#### 6. Порядок реализации

1. Сначала Conversation Context: session lifecycle/API, persistent event history, state projection и provenance.
2. Затем `CContextManager` с token budget, детерминированной сборкой и unit tests; подключить к ReAct так, чтобы каждый model call проходил через него.
3. Затем применить тот же механизм к генерации ответа в обычном `CAskService`/Evidence flow, не дублируя логику лимитов.
4. После этого реализовывать planner(cloud)/worker(local), handoff и blast-radius routing (ADR-24), используя компактное состояние и явные evidence refs вместо переноса всей истории между раундами.

* **Не входит в решение:** выбор конкретного tokenizer-библиотеки, точная session SQLite schema, точный набор полей state projection и provider-specific token overhead. Их нельзя выдумывать в реализации: сначала проверить существующие интерфейсы/зависимости и зафиксировать отдельным решением, если выбор влияет на архитектуру.
* **Связь:** ADR-02 (не смешивать conversation с index DB), ADR-08 (secrets/policy), ADR-09 (Evidence limits/Zero-Window), ADR-24 (planner/worker), ADR-27 (порядок закрытия), §49/§50/§64, §89.10/§89.12.
