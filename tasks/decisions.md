# Журнал решений

Только действующие решения. Старый журнал удалён: он описывал архитектуру,
которой больше нет, и не подлежит частичному переносу — переносить «здравые
куски» некуда, пока для них нет места в текущей схеме.

Формат: решение → причина → как проверено. Ничего «на будущее».

---

## 1. Четыре логические роли LLM, alias приоритетнее полей

**Решение.** Модели описываются только ролями `CODER_SMART`, `CODER_LOCAL`,
`THINKER_SMART`, `THINKER_LOCAL`. Конфиг: `llm_<role>_api|model|key|type|alias|
context_window_tokens|output_reserve_tokens`.

- Непустой `alias` перекрывает `api/model/key/type`; это не конфликт.
- Alias разрешается рекурсивно: `THINKER_LOCAL → THINKER_SMART → CODER_SMART`.
  Цикл и неизвестная цель — ошибка загрузки конфига.
- Групповые `llm_coder_alias` / `llm_thinker_alias` применяются к обеим ролям
  группы; per-role alias перекрывает групповой.
- Без alias обязателен только `api`. Пустой `model` допустим для
  `openai-compat` (локальный сервер подставляет загруженную модель); для
  `claude` — обязателен.
- Эскалация внутри роли: `*_LOCAL → *_SMART`. `*_SMART` — терминальная.

**Причина.** До этого в сборке жили две несовместимые системы выбора моделей:
роли `ELlmRole` (оркестратор, историк, анализатор курсора) и пирамида
`Lite/Main/Remote` (`SConfig`, `CModelFactory`, `CAnswerService`, `CReActAgent`).
На штатном конфиге роли были пусты, и `ask` не работал вовсе.

**Проверено.** Живой `reload` реального `~/.fcpp-agent/agent.conf`; тесты
`stage8a`: цепочка alias→alias→endpoint и отказ на цикле.

## 2. Удалено всё, что не участвует в рабочем пути

**Решение.** Удалены из кода, сборки и с диска: `CModelFactory`,
`CModelLevels`, `CModelCascade`, `CReActAgent`, `CAnswerService`,
`CAnswerQuality`, `CEscalatingIntentAnalyzer`, `CIntentAnalyzer`,
`CRequestPipeline`, `CSubtaskComposer`, `CSubtaskOrchestrator`,
`CEvidenceCollector`, `CContextManager`, `CChatContextSource`,
`CCodeContextSource`, `CProjectProfileContextSource`, `IContextSource`,
`CContextDiagnostics`, `SIntent`, `SSubtasks`, `SRequestOutcome`, `SCascade`
и их тесты.

**Причина.** Два параллельных маршрутизатора в одной сборке. Зелёный CI
подтверждал поведение, недостижимое из `ask`, — то есть создавал видимость
покрытия.

**Проверено.** Граф достижимости от `main.cpp`/`CProtocolServer.cpp`:
[`plans/orchestrator_dependency_map.md`](../plans/orchestrator_dependency_map.md).
`CContextManager` отдельно забракован как переусложнённый: идентификация
групп строками, обратный поиск по `m_id` в источниках, три прохода бюджета
на один промпт.

## 3. Бюджет контекста принадлежит LLM-слою

**Решение.** `CLlmLayer` знает окно и резерв роли и сам укладывает промпт.

- Явный `context_window_tokens` из конфига — главнее всего.
- Если он `0`: `GET /props` → `default_generation_settings.n_ctx` (только для
  локальных endpoint), кэш на время жизни слоя.
- Если провайдер не ответил: 4096 и событие `llm.context_window` с
  `source=fallback`. Неизвестное окно **никогда** не считается бесконечным.
- Перед вызовом: `prompt_budget = window − output_reserve − system_prompt`.
- При переполнении выбрасывается **середина** промпта: начало содержит улику,
  конец — сам вопрос. Событие `llm.prompt_truncated`.

**Причина.** `n_ctx_train` (32768) — потолок обучения, а не выданное окно; слот
на живом сервере даёт 8192. Разница вдвое: сервер молча обрезал бы промпт,
и модель теряла бы начало. Бюджет в вызывающем коде означал бы дублирование
знания об окне в каждом вызывающем.

**Проверено.** Живой лог: `llm.context_window {"role":"CODER_LOCAL",
"source":"provider","tokens":8192}`. Тесты `llm_budget_test`: обрезка 20 КБ
до лимита с сохранением `HEAD_MARKER` и `TAIL_MARKER`; промпт в пределах
лимита не трогается.

## 4. Курсорный срез — окно вокруг строки курсора

**Решение.** `CCursorContextAnalyzer` читает ±60 строк вокруг курсора с
жёстким лимитом 10 КБ, сохраняя номера строк в срезе. Усечение — флаг, а не
врезка посреди кода. Строка шире лимита режется по границе UTF-8.

**Причина.** Раньше брался диапазон `m_location.m_line … m_end_line`, то есть
вся сущность: курсор внутри класса на 400 строк отправлял в модель весь класс
и обрубался на 24 КБ посреди функции. Объём большой, нужное место может
отсутствовать.

**Проверено.** Тест `cursor_context_test`: класс на 400 строк, курсор на 200 →
срез содержит строки 195–205, строки 100 и 300 отсутствуют, размер < 2 КБ.

## 5. Заголовки разбираются как C++

**Решение.** `CClang22::parse_translation_unit` определяет язык по расширению:
`.h/.hpp/.hh/.hxx/.ipp` → `-x c++-header`, `.c` → `c`, `.cpp/.cc/.cxx` → `c++`,
`.m/.mm` → Objective-C, неизвестное расширение — решает `libclang`. Явный `-x`
или `--language` из compile arguments не перекрывается никогда.

**Причина.** `libclang` выбирает язык по расширению, и `.h` разбирался как **C**.
В C нет `class` и `namespace`, AST заголовка с C++-кодом пуст, и
`cursor_at` возвращал `nullopt` — корректно, но для неверного языка. Для
C++-агента это означало, что все `.h`-позиции слепые.

Диагноз получен отладчиком, не рассуждением:
`cursor_at(source_file="...CRequestOrchestrator.h", line=62, column=9,
arguments=length 0)` → `{__engaged_ = false}`. Прямая проверка `clang`:
`.h` без `-x` находит 0 узлов `CXXRecordDecl`, с `-x c++-header` — 2.

**Проверено.** Живой `ask` с курсором в `.h` до фикса: `has_symbol: false`,
маршрут `NO_APPLICABLE_CONTEXT`, ответ-пересказ по названию. После фикса:
символ найден, `facts.collected entity=fcpp::CRequestOrchestrator sections=5`,
маршрут `CURSOR_AND_HISTORY_CONTEXT_REQUIRED`, ответ по существу со ссылкой
на строки. Регрессионный тест: `.h` с `namespace demo { class CWidget }`.

## 6. Факты из индекса запрашивает оркестратор

**Решение.** Интерфейс `IFactProvider` (в `include/`), реализация
`CIndexFactProvider` (поверх `CToolRegistry` и `CToolContext`).

- Оркестратор сам вызывает `collect_facts` до генерации, на курсорных
  маршрутах.
- Набор инструментов фиксирован и не зависит от модели: `def` → `outline` →
  `ancestors` → `derived` → `callers`, лимит 20 на секцию.
- Сбой сбора — `EExitReason::FactCollectionFailed` и событие
  `facts.collection_failed`. Это **не** «данных нет».
- Отсутствие сущности (курсора нет) — не сбой: факты не запрашиваются.

**Причина.** Ветка ответа раньше не читала индекс вообще: модель отвечала о
коде, не увидев ни одного символа. Инструменты при этом существовали, но
вызывались только из `handle_tool`.

**Проверено.** Живой `ask`: `facts.collected {entity, sections: 5}`, ответ
содержит реальные члены класса и замечает расхождение с предыдущим ответом
(«в этом заголовке `CCursorContextAnalyzer` только forward-declaration»).

## 7. `project.open` обеспечивает окружение, а не только проверяет

**Решение.** Если `compile_commands.json` не найден ни в одном разрешённом
месте, выполняется один детерминированный запуск:
`cmake -S <root> -B <build> -DCMAKE_EXPORT_COMPILE_COMMANDS=ON` через
`CExecutor` (под закрытой моделью безопасности), затем поиск повторяется.
Каталог `build` создаётся при необходимости.

**Причина.** Только что клонированный проект — штатный сценарий, а не ошибка.
Прежнее поведение отказывало в открытии.

**Проверено.** Живой `open` на чистом каталоге: файл сгенерирован, индекс
построен, `110 files / 5271 symbols`.

## 8. Реестр проектов — свежий, без совместимости со старым

**Решение.** Реестр создаётся заново. `project_id` — от имени проекта,
`canonical_path` уникален. `upsert` использует простой
`INSERT … ON CONFLICT(project_id)`.

**Причина.** Мы разрабатываем новое приложение; переносить строки старого
реестра не требуется. Совместимость со старым форматом — лишний код.

**Проверено.** Удаление `~/.fcpp-agent/{projects/registry.db,sessions.sqlite,
session,db/*}` и последующий `open`: реестр создан, проект зарегистрирован.

## Что не сделано и почему

- **Compile arguments для `.cpp`.** `ask` работает без них (подтверждено),
  но `-I`/`-D` проекта не передаются. Отдельная задача: не смешивать с
  дефектом языка заголовков.
- **Маршрут `NoApplicableContext` без фактов.** Проверено: он наступает только
  когда нет ни истории, ни курсора, и это корректно. Открытый вопрос другой —
  качество ответа, когда в запросе назван класс проекта, а фактов нет: модель
  пишет «можно предположить». Это качество, не маршрутизация.

## 9. Сессия либо есть, либо её нет

**Решение.** Флаг `m_closed`, колонка `closed_at`, `close_session()`,
`close_session_with_event()` и `reopen_session()` удалены. `session.close`
вызывает `delete_session()`: `DELETE` событий и `DELETE` сессии в одной
транзакции.

**Причина.** «Закрытая сессия» — сущность, которой нет в модели: диалог либо
существует, либо нет. Переоткрытие было обходом собственного флага.

**Проверено.** Живой `close`: обе таблицы дают `COUNT(*) = 0` для сессии.
Схема пересоздана без `closed_at`. Поиск `m_closed|closed_at|reopen_session`
по проекту пуст.

## 10. Шесть маршрутов, взаимоисключающие условия

**Решение.** Маршрут выбирается по трём флагам — `is_cursor`, `is_file`,
`is_history` — шестью взаимоисключающими условиями. Порядок проверок ни на что
не влияет: никакая пара условий не может быть истинной одновременно.

| `is_cursor` | `is_file` | `is_history` | Маршрут |
|---|---|---|---|
| 1 | — | 1 | `CursorAndHistoryContextRequired` |
| 1 | — | 0 | `CursorContextRequired` |
| 0 | 1 | 1 | `FileAndHistoryContextRequired` |
| 0 | 1 | 0 | `FileContextRequired` |
| 0 | 0 | 1 | `HistoryContextRequired` |
| 0 | 0 | 0 | `NoApplicableContext` |

**Причина.** Первая версия пятого маршрута опиралась на порядок `if`:
`if (file) … if (history) …`. Перестановка строк меняла поведение, хотя вход
тот же. Для детерминированного дерева это недопустимо.

**Файл без курсора — отдельный случай.** Позиции нет, но файл есть: это не
«нет контекста» и не «курсор не применим». `assess_file` задаёт модели-мыслителю
строгий YES/NO: относится ли вопрос к этому файлу. При YES содержимое файла
(любой тип: `.cpp`, `.h`, `.md`, `.txt`) уходит в промпт; при NO запрос
завершается видимой причиной `FileNotRelevant` с записью в лог.

**Проверено.** Живой `ask` с `--file src/core/CLogger.h` без позиции:
вопрос про класс → `FileAndHistoryContextRequired`, ответ описывает `CLogger`
по содержимому файла; вопрос про RAII → `file.assessed applicable=false`,
маршрут уходит на историю, ответ по существу.

## 11. Сбой и отсутствие данных — разные вещи

**Решение.** `IndexUnavailable` (а не `FactCollectionFailed`): текст сбоя
содержит `db_path`, `exists`, `stat_error`, стадию и сущность. Preflight в
фасаде проверяет окружение до входа в оркестратор: проект открыт, файл БД
существует, БД открывается, состояние индекса `Ready`.

**Причина.** «Cannot open project index» без пути и стадии — загадка, а не
диагностика. Недоступность индекса — авария, требующая разбора, а не штатное
«данных нет».

**Проверено.** Ветка срабатывает только при повреждённой или отсутствующей БД;
в обычном запуске preflight проходит до оркестратора.

## 12. История ограничивается у историка, нумерация непрерывна

**Решение.** `CHistorian::assess_relevance` отправляет модели только хвост
диалога: не более 20 пар и не более 6 КБ. Нумерация пар в запросе —
непрерывная `1..N` по отправленному хвосту. Возвращённые номера
пересчитываются в исходные позиции истории перед использованием.

**Причина.** Раньше склеивались все пары, какие есть, а LLM-слой обрезал
промпт по байтам, выбрасывая середину. Нумерованный список после такого
разреза указывал на удалённое содержимое: модель возвращала номера, не
соответствующие парам, валидатор отвергал ответ, эскалация повторяла ту же
операцию с тем же результатом. Отсюда `empty model response` на обоих уровнях.

**Проверено.** Тест `historian limits offered history and maps numbers back to
full history`: 30 пар → отбрасываются старые, номер 1 указывает на первую
отправленную пару и пересчитывается в её позицию в полной истории; в промпте
нет отброшенных пар.

## 13. Резерв ответа не съедает окно

**Решение.** Если `output_reserve >= window - window/2`, резерв урезается до
`window - window/2`, пишется событие `llm.reserve_clamped` с исходным и
фактическим значением.

**Причина.** Резерв 4096 при окне 4096 оставлял на промпт ~1900 токенов.
Любой реальный контекст резался до нескольких сотен токенов, и запрос
уничтожался. Это ошибка конфигурации, которую нельзя принимать молча.

**Проверено.** Живой прогон: `llm.reserve_clamped {configured_reserve: 4096,
effective_reserve: 2048}`, обрезка промпта упала с 15038 до 2558 байт, ответ
построен по делу.

## 14. Окно удалённой модели задаётся в конфиге, фолбэк 8192

**Решение.** Для удалённых endpoint проба `/props` невозможна. Окно берётся из
`llm_<role>_context_window_tokens`; при отсутствии — фолбэк 8192 с
предупреждением `llm.context_window`, где указаны `endpoint` (local/remote),
`probe` (failed/unsupported) и подсказка про ключ конфига.

**Причина.** Фолбэк 4096 при резерве 4096 оставлял почти нулевой бюджет.
8192 — минимальное значение, при котором промпт сохраняет смысл.

**Про числа провайдера.** «1M всего / 944K на выход» — это окно входа и потолок
генерации, а не деление бюджета. В конфиг пишется окно входа
(`context_window_tokens="1000000"`) и собственный резерв
(`output_reserve_tokens="8192"`), а не 944K.

**Проверено.** Лог содержит `source: fallback`, `endpoint: remote`,
`probe: unsupported`, `hint: set llm_<role>_context_window_tokens`.

## 15. В журнале нет абсолютных путей

**Решение.** События и тексты ошибок содержат только имена файлов, каталогов,
`project_id` и стадию. Абсолютные пути (`db_path`, `project_root`,
`clang_path`, полный путь файла) в журнал не попадают.

**Причина.** [`plugin_api.md`](../plugin_api.md) прямо запрещает абсолютные
пути в журнале: лог уходит в багрепорты и CI-артефакты, а пути раскрывают
структуру файловой системы пользователя. Кроме того, пути делают логи
несравнимыми между машинами.

**Проверено.** Поиск полей `db_path`/`project_root`/`clang_path` в коде —
отсутствует; поиск `/home/` в свежем `agent.jsonl` после живого `ask` — 0 строк.

## 16. Сбой источника не подменяется сбоем курсора

**Решение.** `choose_root()` записывает первую конкретную причину отказа в
`result.m_exit_reason` до возврата `ERootChoice::Failure`. Сбой истории даёт
`HistoryRelevanceFailed`, сбой чтения файла — `FileRelevanceFailed`, сбой
курсора — `CursorRelevanceFailed`.

**Причина.** Раньше причина жила только в локальной переменной `first_failure`,
а ветка `Failure` в `run()` подставляла `CursorRelevanceFailed` для любого
сбоя. Результат и журнал сообщали про курсор даже тогда, когда курсора в
запросе не было вовсе: диагностика указывала не на сломанное звено.

**Проверено.** `tests/orchestrator_routes_test.cpp`: сценарий с нарушением
контракта нумерованного списка истории даёт `HISTORY_RELEVANCE_FAILED` в
`request.finished`, сценарий с нечитаемым файлом курсора —
`CURSOR_RELEVANCE_FAILED`.

## 17. Обрезанный промпт не эскалируется

**Решение.** Если попытка роли завершилась неудачей, а промпт был урезан по окну
(`llm.prompt_truncated` сработал), переход на резервную роль не выполняется.
Возвращается ошибка первичной роли с добавкой
`not escalating: the prompt did not fit the role context window`.

**Причина.** Пустой или невалидный ответ на урезанный промпт говорит о размере
промпта, а не о возможностях модели. Повтор того же слишком длинного промпта на
другой роли падал так же, но после ещё одного полного таймаута: пользователь
ждал два запроса подряд, чтобы получить ту же ошибку.

**Проверено.** `tests/llm_budget_test.cpp` — два зеркальных сценария: при
урезанном промпте вызвана ровно одна роль и `m_escalated` = false; при
поместившемся промпте эскалация выполняется как раньше.
