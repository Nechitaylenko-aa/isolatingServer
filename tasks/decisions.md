# Журнал архитектурных решений (fcpp-agent ADR)

**Незыблемые принципы:**

1. **Unix:** делать одно, но делать хорошо. Только C++/CMake/Ninja. Никакого функционала сверх ТЗ.
2. **Закрытая безопасность:** всё, что явно не разрешено, — запрещено.
3. **Zero-Search:** агент ничего не ищет и не угадывает. У каждой сущности строгое место (флаг / конфиг / стандарт). Нет в указанном месте — нет в природе → генерация нового или FAIL.

## Блок 1: Инфраструктура, CLI и Хранение данных

### ADR-01: Точный набор CLI-команд (Пункт 1)
* **Контекст:** Минимальный расширяемый набор команд. CLI — тонкий клиент к deterministic API (не ядро).
* **Предложенное решение:**
  - **MVP (жёстко):** `init`, `open <path>`, `close`, `projects`, `ask "<text>" [--json]`, `build [target]`, `test`, `tidy`, `status`, `index <status|refresh|rebuild>`.
  - **Флаги:** `--config PATH`, `--project PATH`, `--compile-commands PATH`, `--yes`, `--json`, `--verbose`.
  - **Exit codes:** `0` success; `1` typed error (§59); `2` usage error.
  - **Вывод:** human-readable по умолчанию; `--json` — machine-readable. Стриминг активен всегда.
  - **REPL:** только если stdin — TTY. Голый текст = `ask`. Без меню и подсказок-эвристик.
  - **Запрещено в MVP:** `serve`, `use`, `config`, GUI-подобные интерактивные сценарии, авто-роутинг admin-команд через LLM.
  - Все команды = 1:1 методы Agent API.

* **Статус:** ✅ Утверждено

### ADR-02: Точная SQLite schema и механизм миграций (Пункты 2, 19)
* **Контекст:** Персистентный индекс. Версионируемая схема, независимая от версии агента/API.
* **Предложенное решение:**
  - Одна БД на проект, вне исходников: `~/.fcpp-agent/db/<hash>/index.db`. `PRAGMA journal_mode=WAL; foreign_keys=ON; busy_timeout`.
  - **Таблицы (суть):** `schema_meta(key,value)`; `project(canonical_path,build_dir,last_indexed_at,generation)`; `index_generation(generation,state)`; `file(path,generation,mtime,size,hash)`; `symbol(id,generation,usr,kind,qualified_name,file_id,parent_id,flags)`; `symbol_location(symbol_id,file_id,line,col,end)`; `include(from_file,to_path,resolved_file)`; `inheritance(derived,base,access)`; `override(method,base_method)`; `reference(symbol_id,file_id,line,col)`; `call(caller,callee)`; `compile_command(file_id,directory,arguments)`.
  - **Миграции:** нумерованные чистые SQL-файлы `migrations/NNNN_*.sql`; runner читает `schema_meta.schema_version`, применяет по возрастанию, каждая в `BEGIN IMMEDIATE`; ошибка → `ROLLBACK`, стоп. Введение `min/max_compatible_schema`. Downgrade не поддерживается (→ `index rebuild`).
  - Смена семантики индекса → новая generation + reindex, не конвертация на месте.
  - До миграции — бэкап `index.db.bak`.
  - Никаких prompt/LLM-текстов в БД.

* **Статус:** ✅ Утверждено

### ADR-03: Формат project mapping и параллельные сессии (Пункты 3, 20)
* **Контекст:** Сопоставление проекта и его БД; поведение при параллельных CLI.
* **Предложенное решение:**
  - **Zero-Search:** проект определяется строго по каноническому пути CMake-корня — из `--project` или из конфига. Никаких эвристик поиска/подбора.
  - **Единая БД агента:** реестр и индекс хранятся в одной SQLite-БД агента (`~/.fcpp-agent/projects/registry.db`); полный набор миграций применяется к ней целиком.
  - Таблица реестра — `registry_project(project_id PK, canonical_path UNIQUE, db_path, last_opened_at, created_at)` (имя `registry_project`, а не `project`, чтобы не конфликтовать с per-project таблицей индекса `project`). `project_id` — непрозрачный (`project-<hash>`), **не равен пути** (§89.3.1). `db_path` детерминированно из `sha256(canonical_path)[:16]`.
  - Нет пути в реестре и нет `CMakeLists.txt` в нём → FAIL с диагностикой.
  - **Блокировки:** WAL + `busy_timeout` → параллельное чтение, один писатель. Межпроцессно — `flock` на `index.lock`: `SHARED` для readers/refresh, `EXCLUSIVE` для rebuild. Конфликт → `INDEX_BUSY`/`PROJECT_BUSY` (`retryable=true`).
  - `index.rebuild` — атомарно: `BUILDING` → `ACTIVE`; ошибка не уничтожает валидную generation.
  - Пишущие транзакции — `BEGIN IMMEDIATE` + батчевые фиксации.

* **Статус:** ✅ Утверждено

## Блок 2: Индексация, Парсинг C++ и CMake

### ADR-04: compile_commands.json и работа с CMake (Пункты 6, 16)
* **Контекст:** Источник флагов компиляции для libclang; политика post-patch сборки.
* **Предложенное решение:**
  - **Zero-Search. Только три источника, по приоритету:**
    1. `--compile-commands <path>`;
    2. конфиг проекта (`compile_commands=<path>`);
    3. `<root>/build/compile_commands.json`.
  - Рекурсивный поиск по дереву — **запрещён**. Не найден — **немедленный FAIL** (`COMPILE_COMMANDS_MISSING`). Автогенерация cmake «на угад» — **запрещена**.
  - Без `compile_commands.json` индексация C++ не выполняется (ADR-06).
  - **Post-patch сборка:** строго `cmake --build <build_dir> --target <target>` — инкрементально, конкретный таргет. Без debounce, без clean, без reconfigure в авто-режиме. Изменены CMake-файлы / нет build-dir / `allow_exec=NO` → STOP, сборка не запускается.
  - Результат сборки кэшируется по (generation, target, mtime-набор).

* **Статус:** ✅ Утверждено

### ADR-05: Сущности индекса, stale index и перформанс (Пункты 4, 5, 17, 18)
* **Контекст:** Что извлекать, как определять устаревание и точку обновления, лимиты MVP.
* **Предложенное решение:**
  - **MVP-сущности (libclang):** translation unit/file, namespace, class, struct, union, enum(+constants), typedef/using/alias, function, method, constructor, destructor, variable, field, parameter, inclusion, base specifier, reference, call expression. Хранение: `kind`, `qualified_name`, **USR**, позиция, access, flags. Шаблоны/лямбды/макросы — пост-MVP.
  - **Stale index (по уровню стоимости):**
    1. инвалидация окружения: изменился `compile_commands.json` / `CMakeLists.txt` / версия backend / `schema_version`;
    2. быстрый проход `stat`: `mtime`+`size`;
    3. подтверждение по content hash — только для кандидатов из (2); hash совпал → актуален, только `mtime`;
    4. новые/удалённые файлы → add/drop (CASCADE);
    5. транзитивные зависимости по графу `include` → переиндексируются только затронутые TU (правка `.h` не пересобирает весь индекс);
    6. неразрешимые include/макросные зависимости → `dirty`, консервативный reparse.
  - **`index.refresh`:** для каждого `dirty_tu` (лексикографический порядок) — delete строк TU → parse → batch insert, в рамках активной generation. Пусто `dirty_tu` → no-op.
  - **Контекст в LLM = минимум (Zero-Window):** файлы `.cpp/.hpp` **никогда не отправляются целиком**. Из SQLite/libclang вырезаются строго: тело запрошенного метода (по SourceRange) или сигнатура класса/enum. Зависимости — только «скелет»: forward declarations + public-интерфейс из БД. Приватное и тела inline не передаются.
  - **Лимиты MVP (soft):** ≤5 000 TU, ≤1 млн строк, per-TU timeout, `build_timeout`. Сверх лимита — предупреждение, обработка порциями.
  - **libclang-память:** RAII-обёртки (`CXTranslationUnit/CXIndex/CXString/tokens`), обязательный dispose, `SkipFunctionBodies` где тела не нужны, ограничение числа одновременных TU, опциональный изолированный `IndexWorker`-процесс.

* **Статус:** ✅ Утверждено

### ADR-06: Отсутствие libclang / cmake / clang-tidy (Пункт 12)
* **Контекст:** Поведение при отсутствии инструментов.
* **Предложенное решение:**
  - **Single-user, фиксированная среда (зафиксировано):** агент персональный. Поддерживается ровно один стек — **C++20, clang/libclang 22, CMake + Ninja** (FreeBSD). Любое отклонение — **жёсткая ошибка с описанием и остановкой** без деградации и продолжения. Никаких «вежливых» fallback под чужую среду.
  - **Critical:** `cmake`, `compile_commands.json`, libclang. Нет любого → **жёсткая ошибка конфигурации** (`COMPILER`/`BUILD_NOT_CONFIGURED`), работа прекращается.
  - **Версия libclang/clang (зафиксировано):** целевая — **clang/libclang 22**; она назначается **по умолчанию** в конфиге (`tool_clang_path`) сознательно, чтобы как можно дольше не менять компиляторный фреймворк. Бэкенд абстрагирован (§2.2), версия — деталь реализации. Наличие других версий (14/19/20) не меняет дефолт.
  - **Сборка/инструменты:** **Ninja используется везде, где это даёт выигрыш** (сборка агента, сборка/тесты проектов под управлением агента). При отсутствии Ninja — допустим fallback на генератор по умолчанию (см. ADR-04).
  - **Запрещено:** Tree-sitter, регулярные выражения, «нативные лексеры» как замена компилятора. Любой fallback-парсер даёт ложные доказательства и нарушает §57/§87.
  - **Important:** `clang-tidy`, `ninja`, `ctest` — деградация только этих: `tidy`/`tests` возвращают типизированную ошибку, index/ask/build работают.
  - **`fcpp doctor`:** preflight-таблица инструментов (найден/версия/путь/класс) + команды установки (FreeBSD pkg / Linux). Выполняется на `open`/`init`.
  - Конфиг: `tool_*_path` override (дефолт clang → llvm22); `enable_tidy=YES|NO`. Агент не устанавливает пакеты.

* **Статус:** ✅ Утверждено

## Блок 3: LLM, Безопасность и Бюджет контекста

### ADR-07: Интеграция с LLM (Пункты 7, 8, 9)
* **Контекст:** Формат обмена, настройки llama-cpp, стриминг.
* **Предложенное решение:**
  - **Формат:** лаконичный XML в стиле Aider (`<intent>`, `<answer>`, `<patch>`), не Tool Calling. Причина: LLM не оркестратор (§5/§83); XML стримится и парсится одинаково на всех backend. Парсер — тег-парсер (не regex), валидация по enum, 1 retry-repair → `LLM_INVALID_RESPONSE`.
  - **llama-cpp `prompt_cache` обязателен:** неизменяемый префикс (system prompt + схема БД + few-shot) на роль, детерминированный порядок контекста → считается только суффикс. `temperature` низкая для lite; фиксированный `seed`; keep-alive весов.
  - `same_as_main` резолвится router; роли не привязаны к моделям.
  - **CLI-стриминг обязателен:** стримится `<answer>`; `<intent>`/`<patch>` аккумулируются и валидируются целиком.
  - Отмена — cooperative; частичный XML не применяется.

* **Статус:** ✅ Утверждено

### ADR-08: Безопасность: whitelist и подтверждения (Пункты 10, 11)
* **Контекст:** Что выполняется без вопроса, что требует Y/N.
* **Предложенное решение:**
  - **Закрытая модель:** Effect вычисляет deterministic core (`READ_ONLY < WRITE_SOURCE < EXECUTE < WRITE_BUILD`), не LLM.
  - **Whitelist (без подтверждения, при `allow_*`):** read = index/outline/callers/callees/refs/includes/status; exec = `cmake --build`, `cmake -S -B`, `ctest`, `ninja`, `tidy`. Проверка по `argv`: basename ∈ whitelist + допустимые флаг-шаблоны.
  - **Инъекции:** запрещены shell-метасимволы (`;|&&$(...)`), redirection, выход за build-dir. Вызовы — только через `execv(argv)`, не через shell.
  - **Обязательный Y/N:**
    - `WRITE_SOURCE` (`apply_patch`): показ diff, применение только после `Y`; non-interactive — FAIL без `--yes`.
    - Любой `EXECUTE` вне whitelist / любой shell → Y/N; non-interactive → FAIL.
  - **Запрещено:** `rm`, `curl`, `wget`, `sh -c`, `perl -e`, `sed -i`, `awk` для правки исходников (§45).
  - Клиент не повышает permission через API (§89.40). Секреты не попадают в diff/log/prompt (§61).

* **Статус:** ✅ Утверждено

### ADR-09: Context Budgeting, Subtasks, Remote (Пункты 13, 14, 15)
* **Контекст:** Упаковка контекста, подзадачи, изоляция выполнения.
* **Предложенное решение:**
  - **Zero-Window:** в LLM уходит технический минимум из Evidence. Никаких файлов целиком. Строго: сигнатуры / тела затребованных методов / relationships. Зависимости — только скелет (forward decls + public API из БД). Раскрытие глубже — ленивое, по запросу planner'а.
  - **Лимиты на секцию:** `max_source_lines`, `max_symbols`, `max_callers`, `max_callees`, `max_refs`. Превышение → детерминированный top-N + summary. Дедупликация общих заголовков. Стабильный порядок секций (под prompt_cache).
  - **Subtasks:** `allow_subtasks=NO` → дочерних задач нет. При `YES` — отдельный subsystem; child наследует snapshot (project/session/editor/generation), возвращает только Evidence родителю. В v2.0 не обязателен.
  - **Изоляция:** `exec_target = local | docker | ssh`; единый `BuildSystem`-интерфейс, разные backend выполнения. Index/файлы локальны; на удалённую сторону — только команда. Подчиняется ADR-08; секреты не покидают хост.

* **Статус:** ✅ Утверждено


### ADR-10: Детерминированная обработка галлюцинаций и каскад моделей (Пункт 7.1)

* **Контекст:** Обнаружение ошибок локальных/слабых моделей и автоматическое делегирование (Lite → Main → Cloud).
* **Предложенное решение:** Триггеры детерминированного обнаружения глюков (Glitches/Hallucinations):
1. Агент считает ответ модели ошибочным, если срабатывает хотя бы один объективный критерий:
  - Syntax Fail (Нарушение формата): Модель выдала невалидный XML/JSON, не закрыла тег <patch> или выдала пустой ответ.
  - Reference Fail (Вымышленные сущности): Модель предлагает изменить метод или файл, которого нет в индексе SQLite (галлюцинация путей или имён).
  - Compilation Fail (Сломанный код): Код после применения <patch> не проходит синтаксический чек через libclang (ошибки компиляции, которых не было до патча).
  - Loop Fail (Зацикливание): Модель генерирует повторяющиеся токены или бесконечно вызывает одну и ту же подзадачу (превышен таймаут или лимит итераций).
2. Путь решения: Каскад моделей (Model Fallback Cascade):
Уровни моделей жестко прописываются в agent.conf (например: lite = Qwen-2.5-7B-Local, main = DeepSeek-R1-Local/32B, cloud = Claude-3.5-Sonnet-API).При обнаружении глюка запускается автоматическая цепочка:
	1. Шаг 1 (Самоисправление): На уровне lite делается ровно один (1) автоматический ретрай с добавлением ошибки в контекст («Ты нарушил XML-формат/сломал компиляцию, исправься»).
	2. Шаг 2 (Эскалация на Main): Если ретрай на уровне lite снова выдал ошибку — сессия замораживается, контекст передается на уровень main (более тяжелая локальная модель).
	3. Шаг 3 (Эскалация на Cloud): Если main выдает синтаксический брак или ломает код — запрос уходит на самый верхний уровень cloud (при условии, что в конфиге прописан API-ключ облачной модели).
3. Жесткий FAIL-safe стопор:
Если самый высокий доступный уровень модели (например, cloud или main, если облако отключено) не смог решить задачу за 1 ретрай, агент полностью останавливает выполнение:
	• Состояние файлов проекта автоматически откатывается до исходного (/revert / git checkout).
	• Выводится строгое сообщение:fcpp-agent: Ошибка обработки запроса. Цепочка моделей [Lite -> Main -> Cloud] исчерпана.
Причина: [Конкретный триггер, например: Патч нарушает компиляцию в src/main.cpp:42]
Действие: Измените ваш запрос или переключите конфигурацию моделей.
4. Запрещено: Бесконечные циклы ретраев, молчаливое игнорирование ошибок компиляции, применение «битых» патчей в надежде, что пользователь исправит руками.
* **Статус:** ⏳ На рассмотрении

### ADR-12: Политика версионирования схемы и порядок этапов (LLM last)

* **Контекст:** До первого рабочего релиза схема активно меняется; при этом архитектура требует детерминированного ядра и запрещает LLM быть оркестратором (§5/§83/§92).
* **Предложенное решение:**

  **1. Версионирование/миграции — только с v1 (✅ принято).**
  - До первого работающего релиза — **никаких нумерованных миграций и версий схемы**. Схема задаётся **единым baseline-файлом** (`CREATE IF NOT EXISTS`), свободно правится при разработке.
  - Строгое версионирование включается ровно в момент «v1 заработал», когда появляется персистентность, которую нельзя терять.
  - **`index.db` — кэш, восстановимый из исходников** → при несовместимости: не конвертировать, а **пересоздать generation**. Миграции для кэша не обязательны.
  - **`registry.db` — единственное пользовательское состояние** (список проектов), но восстановимо повторным `open` при single-user.
  - Тесты не привязываются к точной версии схемы.

  **2. Порядок этапов: детерминизм вперёд, LLM — в последнюю очередь (✅ принято).**
  - **LLM last** — модель только интерпретирует запрос и формирует ответ/патч.
  - **`Intent` IR и Evidence Planner — детерминированный код**, не LLM: `Intent`-структуры, table-driven `Intent → [tools]`, Context Budget, patch validate/policy — всё делается **до** подключения модели.
  - «Intent last» **неверно**; «LLM last» — верно.

  **3. Точный порядок реализации.**
  1. **8a — инфраструктурный минимум:** `allow_read/write/exec` (§47), `fcpp doctor` (ADR-06), structured logging (§60), персистентная сессия («текущий проект»).
  2. **6a — детерминированное ядро запроса:** `Intent` IR, Subject Resolver (надстройка над `cursor_at`), Evidence Planner (table-driven). Проверяется ручным `Intent` в CLI без LLM.
  3. **7a — patch-pipeline без LLM:** parse → validate → policy → apply → post-patch `cmake --build --target`; вход — патч из файла/stdin. Требует §47 (`allow_write`) и интеграции `CExecutor`.
  4. **8b — Agent API:** CLI становится тонким клиентом (§93); API **не** экспонирует `Intent/Area/Relation` (§89.39).
  5. **6b — LLM-биндинг:** `lite` заполняет `Intent`; `main` формирует ответ/патч (llama.cpp, `prompt_cache`, стриминг, XML Aider-style).
  6. **7b — полный цикл изменения:** LLM генерирует патч → конвейер 7a.
  7. **Каскад моделей (ADR-10) + benchmark классификации (§71–72).**

  **Ограничения порядка:** patch-apply не делать раньше §47; API не связывать с `Intent`; `CExecutor` подключать до patch-apply.

* **Статус:** ✅ Принято

### ADR-11: API-поверхность слоя libclang (что берём от clang заранее)

* **Контекст:** Детерминированный core должен получать от libclang заранее известный, стабильный набор запросов. Состав API фиксируем до реализации, чтобы не менять его при добавлении инструментов.
* **Предложенное решение:**

  **Принципы слоя.**
  - Слой **не строит графы/резолвинг сам** — максимально делегирует libclang (детерминизм, меньше собственного кода).
  - Все запросы — по стабильным идентификаторам (`USR`), не по именам/путям.
  - Каждый запрос — типизированный результат + типизированная ошибка (Секция 3).
  - libclang — только read-only анализ. Изменение кода — через patch (ADR-04/§45).

  **A. Локация курсора → сущность (§21, §51).**
  - `cursor_at(file, line, col)` → `USR` (ближайшая семантическая сущность; предок при попадании в тело).
  - Семантика «этот класс/эту функцию» через ближайший охватывающий `USR`.

  **B. Описание сущности (§34, §35).**
  - `outline(USR)` — дети (методы/поля/вложенные типы) с сигнатурами, access, флагами.
  - `signature(USR)`, `source_range(USR)` (для Zero-Window-среза §34/ADR-05).
  - `get_canonical(USR)` — каноническая декларация (для дубликатов объявление/определение).

  **C. Типы (§15).**
  - `type_of(USR)` — тип сущности/поля/параметра; `resolve_type` до named-типа.
  - `result_type(USR)`/`param_types(USR)`.
  - `points_to(USR)` / `pointee(USR)` / `referenced(USR)` (последнее — встроенный `clang_getCursorReferenced`, важно для callers).

  **D. Иерархия (ключевой сценарий заказчика).**
  - `base_types(USR)` — прямые базовые типы.
  - `ancestors(USR)` — подъём по цепочке до корня (protected/private/virtual).
  - `derived_types(USR)` — прямые наследники (из БД, т.к. libclang не имеет глобального reverse-поиска).
  - `overrides(USR)` — методы, переопределяющие данный (в наследниках).
  - **`dispatch_targets(USR)` — сквозной резолв виртуального/чисто-виртуального метода до всех реализаций в наследниках:**
    1. `base = get_canonical(USR)`; 2. `derived = derived_types(base)`; 3. `overrides = overrides(base)`; 4. объединить с базовым `USR`.
  - **`base_of_override(USR)` — обратный подъём от реализации к объявляющему базовому методу.** Это два зеркальных запроса (§38).

  **E. Вызовы и ссылки (§36, §37, §39).**
  - `callers(USR)` — места вызовов; через `clang_getCursorReferenced` на `CallExpr`/`DeclRefExpr` (не по имени).
  - `callees(USR)` — что вызывает функция.
  - `references(USR)` — все использования (тип/значение/вызов), позиции.

  **F. Специальные члены (§15).**
  - `specializations(USR)` — ctor/copy/move ctor и dtor, виртуальный dtor.

  **G. Include-граф (§40).**
  - `file_includes(file)` — прямые включения; `included_by(file)` — обратные (из БД).
  - `resolve_include` — резолв `InclusionDirective` в `file` (Zero-Search в пределах известных TU).

  **H. Макросы (пост-MVP, задел).**
  - `macro_definition_at`, `macro_expansions(USR)`, `macro_for_usr`. Заложить в интерфейсе, реализовать позже.

  **I. Диагностики (задел для verify — §42/§43).**
  - `diagnostics(tu)` — ошибки/предупреждения компиляции (используется валидатором патчей, ADR-10 Cascade).
  - `syntax_only_compile(tu)` — проверка «патч сломал/не сломал компиляцию».
  - Точные/системные диагностики при необходимости.

  **J. Обход TU (§15).**
  - `visit_tu(file, visitor)` — детерминированный обход верхнего уровня (без обхода тел, если не нужны).

  **Организация кода (по `rules.md`).**
  - **`IClang` (`include/fcpp-agent/IClang.h`) — ВСЕ обращения к libclang идут через этот виртуальный интерфейс** (запросы A–J). Application-код и прогрев кэша зависят только от `IClang`, никогда — от libclang напрямую.
  - **`CClang22` (`src/index/CClang22.{h,cpp}`) — реализация `IClang` под целевую версию clang 22** (дефолт, ADR-06). Добавление другой версии — новый класс (`CClangXX : public IClang`) без изменения core (§2.2, безболезненная версионность).
  - `ICompilerIndex` — **высокоуровневый** интерфейс графа отношений (DERIVED, по семействам D/E/G/I). Реализация **строит граф из SQLite**, а libclang (`IClang`) использует только для первичного наполнения/refresh. `dispatch_targets`/`included_by`/`derived_types` живут здесь, не в `IClang`.
  - `CClangVisitor` — RAII-обёртки над `CXIndex/CXTranslationUnit/CXString/токены` + обход AST (обязательный dispose); используется только внутри `CClang22`.
  - Разделение уровней: `IClang` = низкоуровневый «сырой» доступ к clang; `ICompilerIndex` = детерминированный граф из индекса. Прогрев кэша идёт через `IClang` (или через `ICompilerIndex`, который внутри вызывает `IClang`).
  - Фабрика `create_clang_backend(...)` возвращает `std::unique_ptr<IClang>` по конфигу (`tool_clang_path`/дефолт llvm22).

  **Плюсы `IClang` (принято):** (1) bypass libclang в тестах — подмена стабом; (2) версионная расширяемость без правок core; (3) единая точка RAII и изоляции crash-prone libclang (при желании — за `IndexWorker`-процессом).

  **Уточнение (моё предложение):** `IClang` действительно абстрагирует доступ к clang, но **граф отношений (callers/derived/overrides/dispatch) должен собираться один раз в SQLite и обслуживаться `ICompilerIndex`**, иначе каждый запрос tools снова пойдёт в libclang и вернётся зависимость от скорости clang (§3.3/§63). Т.е. `IClang` = «как читать clang», `ICompilerIndex` = «граф, из которого отвечают tools».

  **Удовлетворённые требования:** §15 (сущности), §36–40 (tools), §42–44 (compile/patch-verify), §21/§51 (cursor/Subject), §38 (overrides/inheritance).

  **Альтернатива:** собственная генерация AST через Clang LibTooling — мощнее, но тяжелее; libclang достаточно для read-only индекса MVP, а позже back-end абстракция (§2.2) позволяет добавить LibTooling без изменения application-кода.

* **Статус:** ⏳ На рассмотрении
