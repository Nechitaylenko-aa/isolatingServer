# fcpp-agent — plugin API

Версия контракта: 2 (жёсткая адресация диалога через `session_id`).

Документ описывает JSON-сообщения между плагином и агентом. Плагину не требуется знать внутренние C++-типы, Intent, Evidence, инструменты или устройство индекса.

## 1. Транспорт

- Кодирует каждое сообщение как отдельный JSON-объект.
- Для stdio-транспорта: одна JSON-строка на запрос и одна JSON-строка на ответ; сообщения разделяются переводом строки.
- Поле `id` задаёт клиент и получает обратно без изменений.
- Для диагностики тот же `id` записывается как `request_id` в журнале агента; при вызове C++ API без клиентского ID агент генерирует внутренний ID.
- Один запрос — один ответ. Асинхронные события и поток уведомлений пока не входят в контракт.
- Ошибка разбора запроса не завершает протокольный цикл.

## 2. Общая форма

Запрос:

```json
{ "id": "req-1", "method": "agent.status", "params": {} }
```

Успешный ответ:

```json
{ "id": "req-1", "result": { "state": "COMPLETED" } }
```

Ошибка:

```json
{
  "id": "req-1",
  "error": {
    "code": "InvalidRequest",
    "message": "Human-readable description",
    "details": {}
  }
}
```

Коды ошибок — регистрозависимые строки с именами C++-enum: `InvalidRequest`, `SymbolNotFound`, `Ambiguous`, `NotUnderstood`, `IndexNotReady`, `IndexStale`, `IoError`, `ProjectNotOpen`, `PermissionDenied`, `PatchInvalid`, `PatchApplyFailed`, `BuildFailed`. Клиент не должен зависеть от текста `message`; показывать его пользователю допустимо. `Ok` — значение отсутствия ошибки и не должно встречаться в объекте `error`.

## 3. Проект и сессия

### `open`

Открывает проект; обычно вызывается при открытии проекта в IDE.

```json
{ "id": "open-1", "method": "open", "params": { "projectRoot": "/absolute/path/to/project" } }
```

Успех содержит `result.state = "READY"`, `result.project_id` и `result.session_id`. При первом открытии проекта агент создаёт активную сессию; при повторном открытии возвращает существующую активную сессию проекта. Клиент должен сохранить возвращённый `session_id` и передавать его в каждый `ask`.

### `close`, `status`, `project.list`

```json
{ "id": "close-1", "method": "close", "params": {} }
{ "id": "status-1", "method": "status", "params": {} }
{ "id": "projects-1", "method": "project.list", "params": {} }
```

### `session.open`

Создаёт отдельную разговорную сессию. Для диалога в открытом проекте обычно не требуется: используйте `session_id`, возвращённый методом `open`. Метод оставлен для клиентов, которым нужна отдельная сессия без автоматического выбора сессии проекта.

```json
{ "id": "session-1", "method": "session.open", "params": {} }
```

Ответ содержит `result.session_id` и `result.state = "READY"`.

### `session.resume`

Восстанавливает адрес активной сессии проекта. Сначала проект должен быть открыт через `open`; без открытого проекта агент возвращает ошибку, а не выбирает произвольную сессию из БД.

```json
{ "id": "session-resume-1", "method": "session.resume", "params": {} }
```

Можно передать `projectId`, если нужно явно указать уже открытый проект. Успех содержит `result.project_id` и `result.session_id`.

### Пример CLI

```sh
# Открыть проект; команда выводит project_id и session_id
fcpp-agent open /absolute/path/to/project

# Каждый ask использует адрес сессии, полученный при open
fcpp-agent ask "Что делает этот метод?" --session session-...

# В отдельном запуске восстановить сессию, указав проект
fcpp-agent session resume /absolute/path/to/project

# Закрыть конкретную сессию
fcpp-agent session close session-...
```

CLI — такой же клиент API, как IDE-плагин. Команда `open` выводит `session_id`; `session resume` в однократном CLI-процессе принимает путь проекта (либо восстанавливает ранее открытый проект, если путь не указан и сохранённый адрес доступен).

### Рекомендуемый жизненный цикл клиента

1. IDE/CLI вызывает `open` с корнем проекта.
2. Сохраняет `result.project_id` и `result.session_id`.
3. Каждый `ask` передаёт сохранённый `session_id`.
4. Если клиент потерял адрес сессии, но проект уже открыт, вызывает `session.resume`.
5. При смене проекта использует адрес, возвращённый новым `open`; не переносит старый `session_id` в другой проект.
6. При закрытии диалога вызывает `session.close`; закрытая сессия больше не принимается в `ask`.

### `session.close`

```json
{ "id": "session-close-1", "method": "session.close", "params": { "session_id": "session-..." } }
```

### `session.update_context`

Передаёт JSON-контекст, который должен быть валидным JSON любого типа.

```json
{
  "id": "ctx-1",
  "method": "session.update_context",
  "params": {
    "session_id": "session-...",
    "context": { "goal": "Inspect API", "constraints": ["Keep public API stable"] }
  }
}
```

## 4. Запрос пользователя: `ask`

Минимальный запрос:

```json
{
  "id": "ask-1",
  "method": "ask",
  "params": {
    "session_id": "session-...",
    "text": "Почему здесь используется virtual?",
    "editor": {
      "file": { "path": "src/model/shape.hpp" },
      "cursor": { "line": 25, "column": 15 }
    }
  }
}
```

Поля:
- `text`: пользовательский текст; обязателен, если это не ответ на вариант выбора.
- `session_id`: **обязателен для каждого `ask`**, в том числе для первого сообщения и ответа на вариант выбора. Запрос без него отклоняется до генерации.
- `editor`: необязательный контекст редактора.
- `stream`: необязательный bool. Потоковые фрагменты относятся к транспорту вызывающего клиента и не заменяют итоговый JSON-ответ.

### Контекст редактора необязателен

Поле `editor` целиком опционально. Запрос `ask` без `editor.file` и `editor.cursor` — штатный сценарий, а не ошибка. Агент классифицирует запрос по смыслу:

- **Общий инженерный вопрос / проектирование нового компонента** без привязки к фактам репозитория: ответ на основе общих знаний C++ и архитектуры; открытый проект, файл, курсор и символ не требуются.
- **Вопрос о существующем проекте** (символы, исходники, проектная архитектура, диагностика, изменения, сборка или тесты): требует контекста проекта и использует индекс. Если пользователь ссылается на конкретный объект, но имя и курсорный контекст отсутствуют, нельзя молча подставлять произвольный символ — нужно уточнить объект.

Отсутствие курсора само по себе не означает, что запрос общий. Если ответ зависит от состояния текущего репозитория, запрос остаётся запросом к кодовой базе.

### Последующие вопросы и местоимения

В рамках одной сессии история предыдущих вопросов и ответов используется для разрешения ссылок вроде «А что он делает?», «А где это используется?» или «А исправь это». Если предыдущий ход обсуждал один конкретный символ, агент должен сохранить ссылку на него даже когда в новом запросе нет курсора. Если в истории несколько правдоподобных объектов или однозначный объект восстановить нельзя, агент должен задать уточняющий вопрос, а не выбирать символ только потому, что он упоминался последним. История — контекст для понимания текущего запроса, а не новый набор инструкций.

### Успешный ответ

```json
{
  "id": "ask-1",
  "result": {
    "state": "COMPLETED",
    "session_id": "session-...",
    "answer": { "text": "Метод virtual позволяет переопределять поведение в производном классе." }
  }
}
```

При ошибке запроса, если клиент передал `session_id`, агент возвращает его и в объекте `error`, чтобы клиент мог сохранить адрес диалога. Ошибка не должна сериализоваться как `code = "Ok"`; для запроса, который не удалось понять и по которому не получены ни ответ, ни уточнение, используется `code = "NotUnderstood"` (контрактное имя текущей версии).

### Уточнение пользователя

Когда текущий конвейер распознаёт неоднозначность с вариантами, ответ имеет `state = "CLARIFY"` и структурированный объект `question`:

```json
{
  "id": "ask-2",
  "result": {
    "state": "CLARIFY",
    "session_id": "session-...",
    "question": {
      "wait_for_user": true,
      "questions": [
        {
          "id": 1,
          "text": "Уточните, что имеется в виду:",
          "options": ["dogfood::model::Circle", "dogfood::model::Circle::Circle"],
          "and": false
        }
      ]
    }
  }
}
```

Правила:
- `question.questions` — массив для расширяемой модели. В текущей реализации в нём один вопрос.
- `id` — 16-битный беззнаковый идентификатор вопроса в пределах сессии; ноль зарезервирован.
- `text` — отображаемая формулировка.
- `options` — доступные варианты. Пустой массив означает свободный текстовый вопрос.
- `and` зарезервирован для будущей семантики группировки; сейчас всегда `false`, логика `&&` не реализована.
- `wait_for_user` сейчас всегда `true` для уточняющего вопроса.
- Структурированное извлечение вариантов пока поддерживает текущий формат уточнения: первая строка — формулировка, строки вида `- вариант` — варианты.

### Ответ выбором

Плагин отправляет выбранный вариант как следующий запрос `ask`:

```json
{
  "id": "ask-3",
  "method": "ask",
  "params": {
    "session_id": "session-...",
    "answer": {
      "question_id": 1,
      "option": "dogfood::model::Circle"
    }
  }
}
```

Агент проверяет, что вопрос и вариант присутствуют в истории указанной сессии. Выбор записывается как ответ пользователя и передаётся обработчику запроса вместе с историей диалога. В текущем контракте `answer.option` предназначен для выбора из непустого списка вариантов; для свободного ответа используйте обычный `ask` с `text`.

## 5. Обрезка диалога: `question.shrink`

Обрезка реализована как логическая операция над активной проекцией диалога.

```json
{
  "id": "shrink-1",
  "method": "question.shrink",
  "params": {
    "session_id": "session-...",
    "question_id": 105
  }
}
```

Реализация добавляет в append-only журнал событие `session.question_shrunk`. Активная история диалога и реконструируемое состояние логически обрезаются до указанного вопроса включительно; исходные события сохраняются для аудита. Если вопрос не найден в активной истории, `result.shrunk = false` и история не меняется.

При успешном shrink активная проекция оставляет указанный вопрос и всё, что было до него; более поздние элементы перестают участвовать в контексте, восстановлении ходов и проверке вариантов ответа. Физическое удаление из append-only журнала намеренно не выполняется.

## 6. Остальные методы

| Метод | Основное назначение |
|---|---|
| `agent.status` | Состояние агента |
| `agent.capabilities` | Список известных API-методов |
| `config.reload` | Перечитать конфигурацию |
| `index.status` | Состояние индекса |
| `index.refresh` | Обновить устаревшие данные индекса |
| `index.rebuild` | Полностью перестроить индекс |

| `tests` / `tests.run` | Запуск тестов |
| `tool` | Детерминированный запрос к индексу (`tool`, `target`, опционально `limit`) |
| `patch` | Применить unified diff (`payload`, опционально `assumeYes`, `buildAfter`) |
| `doctor` | Проверить окружение |
| `project.profile.set` | Установить паспорт текущего проекта (`profile`) |

Пример запроса к инструменту:

```json
{ "id": "tool-1", "method": "tool", "params": { "tool": "refs", "target": "namespace::Type", "limit": 20 } }
```

## 7. Модель единицы диалога

Внутренняя базовая модель линейна: `TChat` — вектор `SChatItem`. У записи есть 16-битный ID, тип `EChatItemType`, текстовое содержимое и структурированный объект вопроса. Основные типы: `UserRequest`, `AgentQuestion`, `UserAnswer`, `AgentResponse`. Действия агента не входят в эту модель диалога.

В публичном JSON вопрос возвращается как объект `question`; его `questions` — вектор структур `{id, text, options, and}`. В текущей реализации выдаётся один вопрос за раз. `and` зарезервирован для будущей группировки, а не активирует её.

## 8. Совместимость и текущие ограничения

- JSON является внешним контрактом; внутренние C++-структуры не являются частью протокола.
- Поля ответа, не относящиеся к конкретному методу, могут отсутствовать.
- Вызовы синхронные; отдельный event stream пока не реализован.
- Текущая структура допускает массив вопросов, но интерфейс не реализует группу вопросов или семантику `&&`.
- `question.shrink` — заглушка: всегда `false`, никаких данных не удаляет.


## 9. Диагностический журнал

Агент пишет структурированные события JSON Lines в `~/.fcpp-agent/logs/agent.jsonl` (вне каталога проекта). Каждая строка — самостоятельный JSON-объект с `timestamp` (UTC), `level` и `event`.

На уровне API фиксируются `request.start` и `request.finish`. Внутри `ask` события коррелируются тем же `request_id` и показывают этап, длительность и размеры данных без содержимого запросов/ответов:

- `ask.cursor` — был ли передан текущий курсор, удалось ли разрешить символ и иерархический якорь; имена символов и пути не записываются.
- `ask.history_cursor` — сколько недавних ходов с сохранённым курсором проверено и для скольких удалось восстановить символ; имена символов и пути не записываются.
- `ask.start` — длина запроса в байтах, число ходов истории, наличие редакторского контекста и состояние проекта/индекса.
- `ask.project_index` — открыт ли проект, непрозрачный `project_id`, числовое состояние индекса, generation, количество файлов/символов, устаревших файлов и наличие БД индекса.
- `ask.intent.scope` — результат классификации общего инженерного вопроса против вопроса о кодовой базе и выбранный fallback при ошибке.
- `ask.context` — число групп/сообщений, размер собранного контекста либо отказ из-за бюджета.
- `ask.react` — успех ReAct, уровень кандидата, длительность и размер результата.
- `ask.intent` — успешность разбора намерения и структурированные поля Area/Subject/Relation/Projection/Confidence без текста вопроса и имени субъекта.
- `ask.pipeline` — исход и стадия детерминированного конвейера, число запланированных инструментов, число вариантов и длительность.
- `ask.evidence` / `ask.evidence.total` — успешность сбора, число секций, суммарный размер evidence в байтах и длительность.
- `ask.answer` — этап генерации, успешность, размер ответа и длительность.
- `ask.finish` — итог маршрута и причина отсутствия evidence, если конвейер не смог собрать данные.

Журнал намеренно не содержит исходный текст вопроса, prompt, текст ответа модели, фрагменты исходников, содержимое evidence, абсолютные пути, токены или секреты. Поля `index_state` и `candidate_level` — числовые значения соответствующих enum; это внутренние диагностические поля, не часть внешнего API.

## 10. Оценка риска ответа и эскалация

Перед выдачей ответа агент использует отдельный вызов модели-рецензента, когда это возможно. Рецензент возвращает внутреннюю оценку риска 0..100 и вердикт ACCEPT или ESCALATE. При риске от 35 включительно, противоречиях, неподтверждённых утверждениях или некорректном ответе агент пытается повторить генерацию на следующем доступном уровне модели. Если риск остаётся высоким на максимальном доступном уровне, агент не должен выдавать сомнительный текст как проверенный факт.

Оценка риска — эвристический сигнал модели, не калиброванная вероятность истинности. Низкий балл сам по себе не доказывает правильность. Диагностика пишется в stderr; поле оценки не является частью публичного JSON-контракта и не должно интерпретироваться плагином как гарантия корректности.

Чтобы не показывать пользователю непроверенный текст, финальный ответ буферизуется до завершения проверки. В потоковом режиме проверенный ответ отправляется после проверки одним финальным фрагментом; низкая задержка уступает приоритету корректности.


## 10. Валидация входного запроса

- `id` — обязательная непустая строка; она возвращается в ответе без изменения.
- `method` — обязательная строка с известным именем метода.
- `params`, если передан, должен быть объектом. Для методов без параметров поле можно опустить.
- Если известное поле присутствует, оно обязано иметь тип, указанный контрактом. Неверный тип приводит к `INVALID_REQUEST`, а не к молчаливому игнорированию.
- Неизвестные поля игнорируются для совместимости будущих версий.
- Числовые идентификаторы вопроса должны быть в диапазоне 1..65535; `limit`, строка/колонка курсора — неотрицательные 32-битные целые.

| Метод | Обязательные параметры | Необязательные параметры |
|---|---|---|
| `open` | `projectRoot` — непустая строка | — |
| `ask` | непустой `text` **или** `answer`; для `answer` обязательны `session_id`, `answer.question_id`, `answer.option` | `session_id` для обычного запроса, `editor`, `stream` |
| `tool` | непустые `tool`, `target` | `limit` |
| `patch` | непустой `payload` | `assumeYes`, `buildAfter` |
| `session.close` | непустой `session_id` | — |
| `session.update_context` | непустой `session_id`, `context` (любой валидный JSON-тип) | — |
| `project.profile.set` | непустой `profile` | — |
| `question.shrink` | непустой `session_id`, `question_id` в диапазоне 1..65535 | — |
| Остальные методы | — | `path`, если применимо |

Для `ask` поля `text` и `answer` взаимоисключающие. `answer.option` используется только для выбора из непустого списка вариантов; свободный ответ передаётся через `text`. У `patch` пути файлов берутся из unified diff внутри `payload`; отдельное поле `path` не задаёт область применения патча.


### `project.open` diagnostics

При неудачном открытии проектного корня JSONL содержит событие `project.open.failed` с `request_id` и стабильным `failure_stage`. При успехе пишется `project.open.succeeded` со сводкой состояния индекса. `failure_stage` различает канонизацию пути, проверку каталога/CMake, поиск и разбор `compile_commands.json`, миграцию и открытие БД, создание Clang backend, прогрев/обновление индекса и регистрацию проекта. Ответ `project.open` также содержит этап отказа в `message`.


### Повторяющиеся translation units в compile_commands.json

Один и тот же исходный файл может присутствовать в compile database несколько раз, если входит в несколько CMake-таргетов. Текущая схема индекса хранит одну запись `file` и одну compile command на путь в пределах generation. Поэтому `store_inventory` нормализует путь и сохраняет первую встреченную команду для каждого пути; повторные записи не создают дубликаты. Если разные targets компилируют один файл с существенно разными макросами/флагами, индекс использует флаги первой команды — полноценное индексирование нескольких конфигураций требует отдельного изменения модели данных.


## Контракт нормализации путей (обновление 2026-10-27)

Внутреннее представление путей — абсолютный путь с `lexically_normal()`. Относительный путь редактора разрешается относительно канонического корня успешно открытого проекта. Путь `file` из `compile_commands.json` разрешается относительно соответствующего абсолютного `directory`; этот каталог также лексически нормализуется. Разрешение не зависит от текущего рабочего каталога процесса. Для несуществующего файла лексическая нормализация допустима и не требует `canonical()`; проверка существования выполняется на том этапе, где файл действительно нужен.

`CProjectManager::resolve_path()` возвращает пустой путь, если проект не открыт. Неудачная попытка открыть другой проект не подменяет контекст уже активного проекта; вызывающая сторона обязана учитывать результат `project.open` и его `failure_stage`.


### Состояние проекта: идентификация и полное открытие

Read-only методы `project.status` и `index.status` могут восстановить сведения о проекте без индексации. Такой контекст пригоден для статуса, но не означает успешный полный `project.open`. Перед запросами к коду, обновлением/перестроением индекса и сборкой агент должен обеспечить полное открытие; если оно не удалось, запрос не должен продолжаться как будто проект готов.


### Уточнение и текущий ход

Если вопрос не содержит имени метода и нет курсора или исторического курсорного референта, типовой запрос «Что делает этот метод?» возвращает `state=CLARIFY` с `question`, а не `COMPLETED`. Если текущая позиция курсора передана, но не разрешилась, агент не должен подменять её символом из предыдущего хода. История учитывается для понимания ссылки «он» только когда текущий запрос не содержит собственной позиции курсора либо текущий символ успешно разрешён.
