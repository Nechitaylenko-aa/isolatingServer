# Снапшоты через локальный Git (отложено)

Статус: идея принята как направление, реализация отложена до завершения работы
над деревом оркестратора. Ниже — оценка и список того, что нужно решить до кода.

## Суть предложения

Не писать собственный механизм дельт: при старте сессии создать в `/tmp` чистый
git-репозиторий, скопировать туда рабочие файлы, сделать `initial`, а дальше на
каждом шаге коммитить изменённый файл. Откат — `git checkout <шаг>`.

## Что проверено на текущей машине

| Утверждение | Факт |
|---|---|
| «`/tmp` живёт в оперативе (tmpfs), скорость RAM» | **Неверно.** `/tmp` — dataset `zroot/tmp` на 231G (ZFS), не tmpfs |
| «Git сжимает дельты в паки» | Верно, механизм штатный |
| `git` доступен | Верно, версия 2.53.0 |
| `git` разрешён закрытой моделью | **Нет.** `CExecutor` whitelist: `cmake`, `ninja`, `ctest`, `clang-tidy`. Git отсутствует |

## Где идея сильна

- Инкрементальная история без собственного формата дельт.
- `git checkout`/`reset` — предсказуемый и знакомый откат.
- Позволяет откатывать не один патч, а всю цепочку шагов сессии.

## Что нужно решить до реализации

1. **Хранилище.** Либо подтвердить, что ZFS-скорости достаточно, либо выделить
   настоящий tmpfs и явно принять потерю данных при перезагрузке. Сейчас
   утверждение о RAM-скорости ложно.
2. **Права.** Git в whitelist отсутствует. Варианты: расширить whitelist
   (осознанное расширение прав), либо не идти через `CExecutor` (обход политики —
   так делать нельзя). Это архитектурное решение, а не деталь.
3. **Секреты.** Копирование рабочего набора в `/tmp` затянет туда `agent.conf`
   с API-ключами. Нужен явный список исключений (`agent.conf`, `.git`, `build`,
   артефакты индекса). Требование «секреты не покидают хост и не попадают в
   артефакты» уже зафиксировано в требованиях.
4. **Обратный путь.** `git checkout` меняет только кэш. Не описан механизм
   возврата файлов из кэша в реальный проект — это отдельная операция с
   валидацией (сейчас её выполняет `CPatchApplier::revert`).
5. **`git commit -am` работает лишь для отслеживаемых файлов.** Новые файлы
   требуют `add`; удаления — `add -A`. Без этого «просто копирую и коммичу»
   ломается.
6. **Адресация шагов.** `checkout step_2` даёт detached HEAD. Для откета
   рабочего дерева нужны теги (`git tag step_2`) и `reset --hard` либо
   `checkout <tag> -- .`.
7. **Границы применимости.** Сейчас откат нужен только для `patch --build`
   (авто-откат при COMPILATION FAIL уже реализован). Git-кэш имеет смысл для
   многошаговых сессий, которых пока нет. Не строить раньше потребности.

## Связь с существующим

`CPatchApplier` уже умеет откат изменений в памяти и сообщает о неудачном
восстановлении. Git-снапшот не отменяет его, а покрывает другой сценарий —
цепочку шагов. При реализации нужно явно определить, кто владеет откатом на
каждом уровне, чтобы не появилось два конкурирующих механизма.
