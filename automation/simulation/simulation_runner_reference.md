# Симуляционный раннер — справочный документ (сессия 30.08.2026)

Это не техзадание, а конспект уже принятых решений и реально работающего кода —
чтобы через полгода не входить в транс, вспоминая, как это крутится.

## Зачем раннер вообще нужен

**Цель: быстрая текстовая верификация логики автоматизации** — не полноценная
графическая симуляция (это отдельная, отложенная задача на будущее). Раннер
прогоняет уже готовую (после `bind()`) модель Layer 4 (`CAutomationModel`) во
времени и печатает в консоль только содержательные события ("насос запущен",
"переход режима SET_NORMAL → BACKWASH_PREP_1"), а не построчный лог каждого тика.

## Инвариант, который нельзя нарушать

`CAutomationModel::m_atom_sets`/`m_supervisory_atoms`/`m_instruments`/`m_actuators`
— **статические данные**, результат `bind()`. Кодоген читает только их. Раннер —
**отдельный, параллельный потребитель** той же статики + собственное рантайм-
состояние (тени, живые значения). Раннер никогда не мутирует `CAutomationModel`.

## Разделение двух "теней" — ключевое архитектурное решение сессии

Одно и то же имя ("тень") исторически покрывало две разные по природе задачи —
их развели на два независимых класса с разным временем жизни:

- **`ICodegenShadow`** — `build_internal_topology()` / `internal_reactions()`.
  Вызывается **один раз**, при `bind()`. Читает только статику компонента
  (`pump_count()`, роли). Ничего не хранит между вызовами. Пример:
  `CShadowPumpStation` (генерация атомов ротации).

- **`ISimulationShadow`** — `reset_runtime_state()` / `tick(dt)` /
  `apply_command(role, activate)` / `read(role, index)`. Живёт всю сессию
  симуляции, хранит рантайм-состояние. Примеры: `CSimWaterCapacity`,
  `CSimPumpStation`, `CSimValveTwoDirectional`, `CSimValveCut`.

**Важно:** это НЕ множественное наследование одного класса от обоих
интерфейсов — сознательно отвергнутый вариант (много компонентов сейчас,
кратно больше в будущем — 60-100 классов, две независимые оси жизненного
цикла). Каждая пара классов для одного типа компонента — раздельные файлы,
раздельные менеджеры (`CCodegenShadowsManager` / `CSimShadowsManager`).

**Правило "тень нужна всем"**: каждый компонент, участвующий в рантайм-
протоколе раннера, обязан иметь зарегистрированную `ISimulationShadow` в
`m_simShadowsMap` — раннер никогда не хранит/не принимает `NComponent*` там,
где ожидается рантайм-сущность. Глубина реализации конкретной тени растёт по
мере необходимости (простой клапан — почти no-op; ёмкость — обязательно
содержательна с первого дня, без неё вся физика уровня не работает).

## Слой 4 → раннер: как READ и COMMAND реально устроены

### READ — полиморфно через `Instrument`, раннер не знает, что за этим стоит

- `CPhysicalInstrument` — анкер на реальный `CCap`, читает
  `body->get_parameter(index)`. Для параметров рабочего тела (давление,
  перепад давления).
- `CInternalInstrument` — анкер на `NComponent*` напрямую (`m_owner`), НЕ на
  `CCap`. `value()` вызывает `m_owner->read_state_signal(m_role, m_role.index)`.
  Для роли уровня ёмкости, статуса насоса — всего, что физически НЕ параметр
  протекающего тела.
- `CServiceInstrument` — держит `std::function<float()>`. Используется для
  internal variables (motohours) — лямбда замыкает адрес ячейки в
  `m_variable_values`.

**Критерий маршрутизации** — `is_state_derived_role()` /
`kStateDerivedSignalRoles` в `CAutomationAtoms.h`. Роль в списке → не может
быть прочитана как параметр `COperatingBody` → `add_internal_instrument`.
Актуальный список (после правки этой сессии):
`SR_LEVEL_HH, SR_LEVEL_UPPER, SR_LEVEL_MID, SR_LEVEL_BOTT, SR_LEVEL_LL,
SR_PUMP_STATUS, SR_PUMP_STATION_FAIL`.

**НЕ путать** с `ECapSemantics` (`CS_FLOW_SPECIFIC` / `CS_COMPONENT_SCOPED`) —
это отдельная, самостоятельная ось: важна ли идентичность конкретного Cap для
смысла сигнала (давление вход≠выход) или Cap — просто физический якорь на
компонент целиком. Обе оси когда-то были перепутаны в одну переменную — этой
сессией разделены обратно, `is_state_derived_role` отвечает только на вопрос
"параметр тела или нет".

### Обобщённый канал компонент↔тень — `NComponent::set_state_signal`/`read_state_signal`

Не виртуальный, не per-подкласс механизм — **один общий, конкретный** (не
`virtual`) метод прямо на `NComponent`, симметричный уже существующему
`set_error`/`set_state`:

```cpp
void  set_state_signal(const SSignalRole &role, uint16_t index, float value);
float read_state_signal(const SSignalRole &role, uint16_t index) const;
// хранилище: std::map<std::pair<ESignalRole, uint16_t>, float> m_state_signals;
```

Тень (например, `CSimWaterCapacity::tick()`) сама считает физику и пишет
**готовый дискретный результат** по каждой роли — компонент ничего не
сравнивает, только хранит. `CInternalInstrument::value()` читает оттуда же.
Ни `CWaterCapacity`, ни любой другой `NComponent`-наследник НЕ переопределяют
эту пару — она универсальна для любой будущей тени.

### COMMAND — `Actuator` не полиморфен, живое состояние — либо в нём, либо в тени

`Actuator` — один конкретный класс (`anchor`, `role`, `tag`). Раннер решает,
куда девать команду:

```cpp
if (auto *shadow = CSimShadowsManager::instance(target_owner))
    shadow->apply_command(command.role, activate);   // станция/клапан сами решают
else
    actuator->set_live_state(activate);              // простой клапан — прямая запись
```

## `CSimGraphManager` — граф теней, "наложение" клапанов на базовый граф

### Базовый граф — строится один раз, содержит ВСЕ физические пути

`rebuild_base()` обходит `CCap`→`CConductor`→`CCap` (тот же принцип, что
`IInstallationTemplate::find_components_downstream_matching`), но:

- предикат остановки — "есть тень в `m_shadows`" (не тип компонента);
- **не агрегирует** находки по всем `output()` в один список — для каждого
  физического выхода/входа хранится свой отдельный вектор
  (`SEdges::downstream[out_index]`, `upstream[in_index]`) — иначе невозможно
  "наложить" активную ветку клапана поверх;
- разветвление БЕЗ клапана (несколько кепок на трубе) — идём по всем, вектор
  может содержать несколько соседей на одном индексе;
- `is_flow_boundary()` (сейчас `true` только у `CWaterCapacity`) — обрыв
  обхода даже при отсутствии тени; за водоразделом не ищем. Ёмкость — текущий
  водораздел графа теней, глубже неё поиск сознательно не идёт.

### Актуальный граф — проекция базового с учётом текущего состояния клапанов

`rebuild_actual_if_dirty()`, ленивый, по флагу `m_dirty`. Для узла-клапана
выбирается один активный индекс (`CSimValveTwoDirectional::active_branch()`)
либо узел блокируется целиком (`CSimValveCut::is_open()==false`). Реальный
`CCap`/`CConductor` при этом **никогда не мутируется** — клапан меняет только
собственное внутреннее состояние тени, это единственный источник правды.

`mark_dirty()` — колбэк, дёргаемый клапаном из своего `apply_command`.
Механизм подписки — общий, не завязан на конкретные типы клапанов:
`ISimulationShadow` имеет виртуальный `set_topology_changed_callback()` с
пустым дефолтом; в `rebuild()` раннер безусловно вызывает его на КАЖДОЙ тени
(no-op для нетопологических).

### `find_nearest<T>` — проход через цепочку теневых узлов, не один хоп

**Найденный и исправленный в этой сессии баг**: изначальная реализация
делала один шаг и сразу пыталась привести к `T` — если между насосом и
искомой ёмкостью стоял клапан (тоже имеющий тень, но другого типа), поиск
проваливался ВСЕГДА. Исправлено: `find_nearest` продолжает обход от
найденного узла, если он не приводится к `T`, пока не найдёт `T` или путь не
оборвётся.

## `CSimWaterCapacity` — тень ёмкости

`tick(dt)`: считает `rate` (насос до/после через `setPumpPost/Before`),
интегрирует `m_level`, сравнивает с порогами, пишет 5 ролей через
`set_state_signal`.

**Взаимоисключающие ОКНА, не независимые пороги** — иначе при падении уровня
одновременно истинны несколько ролей сразу:

```cpp
bool hh    = level >= hh;
bool upper = level >= upper && level < hh;
bool mid   = level >= mid   && level < upper;
bool bott  = level <  mid;              // ОТКРЫТ СНИЗУ — не ограничен снизу отдельным порогом
bool ll    = level <  bott;             // независимый защитный сигнал, может совпасть с bott
```

`BOTT` обязан быть открыт снизу (`level < mid`, без нижней границы) — иначе
уровень, стартующий ниже нижнего порога окна, попадает в необнаруживаемую
"мёртвую зону": ни одна из ролей не triggers старт насоса → уровень никогда
не меняется → вечный тупик. Это был один из найденных багов сессии.

**Связь насос↔ёмкость** — устанавливается в `CSimulationRunner::process_command`
через `m_graphManager->find_nearest<CSimWaterCapacity>(pump, downstream)`,
не хранится статически — граф теней (актуальный) сам знает, кто сейчас кому
физически сосед.

## `CSimPumpStation` — минимальная тень станции (текущий профиль: "быстрая валидация")

Осознанно НЕ делает ротацию/аварии/выбор конкретного физического насоса —
только `on/off` + `rated_flow_rate()` (design-time паспорт станции целиком).
Полная версия с ротацией (`CShadowPumpStation`, codegen-часть) — для
графического/промышленного профиля, когда до него дойдёт очередь. Разница
между профилями — НЕ enum-параметр фабрике, а просто то, насколько
содержательный класс написан для конкретного типа компонента.

## `CSimulationRunner` — основной цикл

```
step():
    advance_variables()       // internal variables (motohours) — простое приращение
    evaluate_and_diff()        // READ→COMPARE supervisory + активный atom_set + его transitions
    tick_all_shadows()         // tick(m_granularity) КАЖДОЙ зарегистрированной тени, безусловно
    m_time_since_entry += granularity
    m_t += granularity
```

**Важно про порядок**: `evaluate_and_diff()` вызывается ДО `tick_all_shadows()`
— значит на любом тике N условия читают состояние, записанное на тике N-1, не
N. Для медленно меняющихся величин (уровень, motohours) это не критично, но
это осознанный факт архитектуры, не забыть при отладке "почему на первом тике
всё ещё 0".

`evaluate_and_diff()` сравнивает векторы bool с предыдущим снимком, при
расхождении — `apply_actions()` только для атомов, ставших `true` именно
сейчас (сработавших с этого тика, не бывших true раньше). Переход `SAtomSet`
— тоже часть этого механизма (`STransition::trigger`), при срабатывании
сбрасывает `m_time_since_entry`, чистит `m_prev_active_set_results`.

**`process_command`** — вызывается из `apply_actions` на каждую применённую
команду. Только здесь раннер явно знает о конкретных доменных классах
(`CSimWaterCapacity`, `CSimPumpStation`) — единственное осознанное место,
где generic-принцип "раннер не знает домена" не соблюдается, потому что
именно тут нужно физически связать насос с его соседними ёмкостями.

## Найденные и исправленные баги этой сессии (для истории/будущей проверки регрессий)

1. **`Instrument::owner()` отсутствовал на базовом классе** — добавлен
   (невиртуальный дефолт `nullptr`), нужен для построения `m_instrument_index`
   без dynamic_cast-перебора всех подтипов.
2. **`find_nearest` — один хоп вместо цепочки** — см. выше, раздел
   `CSimGraphManager`.
3. **Окна уровня ёмкости — взаимоисключающие пороги без учёта "мёртвой зоны"
   ниже BOTT** — см. выше.
4. **`kStateDerivedSignalRoles` не содержал `SR_LEVEL_UPPER/MID/BOTT`** —
   уровни маршрутизировались как `CPhysicalInstrument` (физика тела),
   `value()` для них не мог работать в принципе. Дополнено.
5. **`tick_all_shadows()` передавал `m_t` (абсолютное время) вместо
   `m_granularity` (приращение)** в `shadow->tick(...)` — реальная ошибка,
   исправлена, хотя не была первопричиной конкретного симптома, на который
   её сначала списали.
6. **`CInternalInstrument::role()` эксперимент автора сессии** сломал
   хранение — из истории: "эксперимент" в сигнатуре `role()` привёл к тому,
   что все 24 инструмента печатались с одинаковой (нулевой/дефолтной) ролью.
   Откачен, `role()` — обычный метод базового `Instrument`, не переопределяется.
7. **`signal_roles_str[]` в `CAutomationAtoms.h` не хватает строк** для
   `SR_JUST_DO_IT`/`SR_MOTO_HOURS` — косметический баг печати (пустой
   `role=` в дампах атомов ротации), НЕ ВЛИЯЕТ на работу раннера, но мешает
   чтению логов. Не исправлено на конец сессии — TODO.

## Открытые вопросы, сознательно отложенные (не забыть, не путать с багами)

- **Затопленные датчики vs пересечение снизу** — `SR_LEVEL_LL`/`SR_LEVEL_HH`
  сейчас не различают "уровень поднимается через порог впервые" от "уровень
  реально упал ниже во время работы" (сухой ход). Настоящая физика: авария —
  это ОТСУТСТВИЕ воды на датчике, не факт пересечения отметки. Требует
  агрегации по нескольким поплавкам ("какие затоплены") — глубже, чем текущий
  `SAggregateSignalSpec` (сейчас только AND, нужно что-то вроде "скопом").
  Осознанно отложено — не костыль вроде смены стартового уровня, а
  полноценная будущая задача.
- **Конфликт двух атомов на один actuator в один тик** — наблюдалось
  безобидно (НС53 дважды подряд получил `activate=1` от двух разных boundary-
  правил) — для насоса идемпотентно, для мешалки/аэратора может быть не
  идемпотентно (start vs stop одновременно). Приоритет между normal-scope
  атомами на одном actuator — не решён.
- **`ESS_TOR_OUT_PRESSURE`/`ESS_TOR_OUT_TURBIDITY` в рантайме** — резолвятся
  через `IInstallationTemplate::resolve_tor_threshold()`, персистентный
  экземпляр шаблона теперь хранится в `CAutomationModel::m_template` (создан
  в `bind()`, не удаляется сразу) — раннер должен получать актуальный порог
  оттуда, не через каст к конкретному ToR-подтипу самостоятельно.
- **Электроприводы клапанов / stuck-check** (травел-тайм, "закрылся ли за 3
  сек") — не реализовано, ждёт первого реального компонента с электроприводом
  (пневмоклапаны в текущей топологии — мгновенный переход, ничего считать не
  нужно).

## Следующее направление (на момент конца сессии)

Палитра компонентов для очистки бытовых стоков — **SBR-реактор, мешалки,
усреднители**. Это осознанно выбранный "второй несхожий сценарий" (принцип:
не обобщать резолвер раньше двух конкретных разных случаев). Ожидаемые
проверки на прочность архитектуры:

- многостадийный цикл (заполнение→аэрация→отстаивание→декантация) как
  ПОСТОЯННО повторяющийся нормальный режим, не редкое исключение вроде
  промывки — тест на то, действительно ли `SAtomSet`/`STransition` общий
  механизм, а не подогнанный под один частный случай;
- мешалка — вероятно первый компонент без входа/выхода потока в привычном
  смысле — тест актуальности anchor-через-Cap для Actuator;
- усреднитель — родственник ёмкости, но другой набор ролей — тест
  универсальности `set_state_signal`/`read_state_signal`;
- многодатчиковая логика уровня в SBR, скорее всего, столкнёт с отложенным
  вопросом агрегации сигналов раньше, чем где-либо ещё.

Потом — газовая ветка (`E_GAS_COMPONENTS`).
